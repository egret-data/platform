# W2 TASK 4, DELIBERATE, three rows of one fact: egret cannot carry a value's
# JAVA BOX TYPE without making the value unusable as a value.
#
# `className` reports `Integer` for a whole number that fits in an i32, `Double`
# for any non-integer and `Long` only past 2^31. Kestra distinguishes more:
#
#   - a whole number from the CONTEXT is an Integer (Jackson's convertValue
#     boxes it) and the same number as a template LITERAL is a Long;
#   - `number(type='LONG')` and `number(type='FLOAT')` return Long and Float
#     boxes regardless of magnitude.
#
# The first cut of this file said "minijinja has one integer type". THAT IS
# WRONG: `ValueRepr` carries U64/I64/U128/I128 unnormalised, and this crate's
# context deserialiser really does route a positive context integer through
# visit_u64 while a literal is always I64. The honest reasons are that the
# split is positive-vs-signed rather than context-vs-literal -- a NEGATIVE
# context integer is I64 too, so keying on it would trade this line for a
# wrong row on the commoner case -- and that minijinja exposes no public
# accessor for the discriminant anyway.
#
# For the LONG/FLOAT pair the reason is different and simpler: carrying the box
# would mean returning an opaque object, which is what BigDecimal/BigInteger
# already are and why THOSE two now answer correctly (fixed in the fix round),
# and it would stop the result being usable as a number -- the filter's whole
# purpose. See runners::filters::java_class_name.
filter-classname-literal-int
filter-classname-of-long
filter-classname-of-float

# 1. Java regex constructs egret refuses rather than mis-answers.
#
# The `regex` crate is a linear-time automaton with no backtracking, so it
# cannot express a lookaround, an atomic group, a possessive quantifier or a
# backreference; and it carries Unicode scripts and categories but no BLOCK
# tables and no `java.lang.Character` predicates. Kestra ACCEPTS all of these,
# so there is no error class to compare against -- the entry stays here rather
# than becoming a free pass in error-class.txt, and
# `runners::filters::a_refused_construct_says_so_rather_than_claiming_the_pattern_is_invalid`
# asserts that each refusal names its own construct.
#
# `runners::javare` translates everything it can instead of refusing: a
# 265-probe sweep found 101 divergences between Java's pattern language and
# the crate's, and after the translation the only ones left are these.

filter-regexmatch-lookbehind
filter-regexmatch-backreference
filter-regexmatch-possessive-quantifier
filter-regexmatch-atomic-group
filter-regexmatch-unicode-block
filter-regexmatch-java-character-predicate
filter-regexmatch-previous-match-anchor
# Java's `$` outside MULTILINE is `\Z`: it matches before a FINAL line
# terminator. The crate's `$` is end-of-haystack. `runners::javare` translates
# `$` to `\z`, which is exact on every subject that does not end in a line

# two could differ. Consuming the terminator instead would answer `regexMatch`
# right and then delete the newline in `regexReplace`.

# 2. minijinja's string-literal lexer is not Pebble's, and this is NOT a
# filter's doing.
#
# Pebble does not process backslash escapes inside a single-quoted string:
# `'(a)\1'` reaches the filter as six characters and `'\\'` as two. minijinja
# reads `\1` as U+0001 and `\\` as one backslash. So a Kestra pattern or
# replacement written with either spelling means something different here
# before any filter sees it.
#
# `filter-regexreplace-escaped-backslash-from-a-variable` is the same
# replacement supplied through the context, and it PASSES -- which is what
# separates "the filter is wrong" from "the literal arrived different". The
# fix belongs in `runners::rewrite` / the environment's lexing, not in
# `runners::filters`.

filter-regexreplace-escaped-backslash
