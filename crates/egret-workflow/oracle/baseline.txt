# W2 TASK 4, DELIBERATE, three rows of one fact: egret cannot carry a value's
# JAVA BOX TYPE without making the value unusable as a value.
#
# `className` reports `Integer` for a whole number that fits in an i32, `Double`
# for any non-integer and `Long` only past 2^31. Kestra distinguishes more:
#
#   - a whole number from the CONTEXT is an Integer (Jackson's convertValue
#     boxes it) and the same number as a template LITERAL is a Long;
#   - `number(type='LONG')` and `number(type='FLOAT')` return Long and Float
#     boxes regardless of magnitude.
#
# The first cut of this file said "minijinja has one integer type". THAT IS
# WRONG: `ValueRepr` carries U64/I64/U128/I128 unnormalised, and this crate's
# context deserialiser really does route a positive context integer through
# visit_u64 while a literal is always I64. The honest reasons are that the
# split is positive-vs-signed rather than context-vs-literal -- a NEGATIVE
# context integer is I64 too, so keying on it would trade this line for a
# wrong row on the commoner case -- and that minijinja exposes no public
# accessor for the discriminant anyway.
#
# For the LONG/FLOAT pair the reason is different and simpler: carrying the box
# would mean returning an opaque object, which is what BigDecimal/BigInteger
# already are and why THOSE two now answer correctly (fixed in the fix round),
# and it would stop the result being usable as a number -- the filter's whole
# purpose. See runners::filters::java_class_name.
filter-classname-literal-int
filter-classname-of-long
filter-classname-of-float

# W2 TASK 4 FIX ROUND 3, DELIBERATE and NOT this module's to fix: egret cannot
# tell Pebble's `null` LITERAL from a TYPO'D VARIABLE at a filter's input.
# `{{ typo | string }}` is a RootAttributeNotFoundException in Kestra and
# renders empty here.
#
# Pebble's `null` is a real literal; minijinja has no such name, so BOTH arrive
# as ValueKind::Undefined. Measured on minijinja 2.24:
# UndefinedBehavior::Strict raises for `{{ typo }}` but NOT for
# `{{ typo | string }}` -- an undefined piped into a filter is simply passed in.
# So this is not a cost of treating an undefined as Kestra's null in
# runners::filters::is_java_null: the typo renders empty either way, and that
# treatment is what makes the six `*-literal-null` entries pass, including
# filter-distinct-literal-null (`<null>`), which no other route can produce.
#
# The real fix is one layer up: if runners::rewrite translated Pebble's `null`
# literal to minijinja's `none`, the literal would be a None and the typo would
# stay an Undefined, and the two could be kept apart. That is a change to the
# REWRITER's vocabulary. Flagged for whoever owns it.
filter-string-undefined-input

# W2 TASK 4, DELIBERATE: `EscapeCharFilter.processMap` allocates a

# comes back `{"a":..,"b":..}`. egret keeps insertion order, like every other
# map path in this crate. Matching would mean porting Java's hash-bucket
# layout into egret to imitate a bug. See runners::filters::escape_char.
filter-escapechar-map-two-keys


# W2 TASK 5, DELIBERATE (1 of 3): egret refuses the THREE pattern letters whose
# output is TEXT OUT OF A LOCALE DATABASE, rather than answering plausibly.
#
# `z`/`zz`/`zzz`/`zzzz` is the zone's CLDR *specific* display name. Measured
# through this harness: Asia/Tokyo is `JST`, Asia/Ho_Chi_Minh is `GMT+07:00`,
# Australia/Eucla is `GMT+08:45`, Europe/Moscow is `GMT+03:00`. tzdb's own
# abbreviations -- which `chrono-tz` exposes and which are the only zone text
# available to egret -- agree for the first and the third and say `+07` and
# `MSK` for the other two. There is no rule that is right for both halves, so
# `runners::javafmt::format_field` refuses with the letter named.
#
# `v`/`vvvv` is the *generic* zone name (`JT` / `Japan Time`), a third CLDR
# table, and is refused for the same reason. **It was missing from the
# alphabet entirely until the fix round's probe sweep**, so egret said
# `Unknown pattern letter: v` where Java says the pattern is valid -- telling
# an author their pattern was wrong when it was not. `B` (the day period as
# text, `in the morning`) is the third and has no corpus entry of its own.
#
# `full` and `long` are the same fact once removed: their CLDR patterns end in
# `zzzz` and `z`, so they inherit the refusal. `medium` and `short` do not and
# both pass.
filter-date-pattern-zone-name
filter-date-pattern-generic-zone-name
filter-date-style-full
filter-date-style-long

# W2 TASK 5, DELIBERATE (2 of 3): egret's `date` filters are English-only.
#
# Kestra's month, day, era and quarter names come from the JVM's CLDR data for
# whatever locale is in force; egret carries the English names and refuses any
# other `locale`, because answering `January` for `locale='fr'` is a silently
# wrong string in a renderer whose whole job is byte fidelity.
#
# Only `en` and `en_US` are accepted, not every English tag, and that is
# measured rather than cautious: `WeekFields.of(locale)` reads the locale's
# COUNTRY, so `en`/`en_US` are Sunday-first with one minimal day while `en_GB`
# is Monday-first with four and `en_VN` -- the harness machine's own default --
# is Monday-first with one. Accepting `en_GB` would answer `w`, `W`, `Y`, `e`
# and `c` wrongly while looking supported. See runners::javafmt::Locale.
filter-date-locale-french

# W2 TASK 5, DELIBERATE (3 of 3): a whole number is Kestra's `Long` here.
#
# `AbstractDate.convert` has branches for `Long` and for `String` and NONE for
# `Integer`, so a context integer small enough to box as `java.lang.Integer`
# falls through to `(String) input` and throws -- while the same digits as a
# template LITERAL are a `Long` and are read as an epoch. `1705314600` is a
# ten-digit epoch second, the commonest number anyone pipes into `date`, and it
# is exactly the range that cannot work in Kestra.
#
# This is the same limit that baselines filter-classname-literal-int, and for
# the same reason: minijinja carries the U64/I64 discriminant but exposes no
# accessor for it, and the split is positive-versus-signed rather than
# context-versus-literal. Given the choice of which side to be right on, egret
# reads every whole number as a Long -- so filter-date-epoch-seconds-literal,
# filter-date-epoch-millis-context, filter-date-epoch-nanos-context and
# filter-date-epoch-nanos-truncating all pass, and this one records the cost.
filter-date-epoch-seconds-context


# W2 TASK 5 FIX ROUND 1, DELIBERATE: egret's DATE RANGE is chrono's, which is
# narrower than java.time's.
#
# A `NaiveDateTime` reaches about +/-262143 years; a `LocalDateTime` reaches
# +/-999999999. So `dateAdd(100000000, 'DAYS')` is `+275814-09-28` in Kestra
# and cannot be represented here. The limit is the crate's, not a choice.
#
# What WAS a choice, and was wrong, is the message: the first cut reported
# `long overflow` -- Java's sentence for genuine `long` arithmetic overflowing,
# a different cause -- and its unit test asserted exactly the two extremes
# (`Long.MAX_VALUE` DAYS, 1e9 YEARS) where the two engines agree, while the
# whole middle diverged silently. Both now separated: `runners::javafmt`
# checks `Math.addExact` first and keeps `long overflow` for it, and says
# `egret's dates are chrono's` for its own limit.
filter-dateadd-past-egrets-date-range

# filter-classname-literal-int. This line records that the `timestamp*` family
# reaches it too.
filter-timestamp-classname
