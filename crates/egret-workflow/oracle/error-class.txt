# Every corpus entry compared by ERROR CLASS instead of by value.
#
# `compare: "error-class"` means tests/oracle.rs checks only that egret ALSO
# fails, never what it says -- because the golden value is a Java exception
# string no Rust port can reproduce byte for byte.
#
# It is also a FREE PASS: such an entry matches on any error at all, including
# `unknown function`, so it is born matching, never enters oracle/baseline.txt,
# and can never fail. A task that cannot reproduce a filter could mark its
# entry error-class and the oracle would go green on work that was not done.
#
# So adding one is a deliberate, reviewable act: this file is asserted to equal
# the set of markers in corpus.json EXACTLY, which makes a new error-class
# entry a one-line diff here rather than a field edit buried in a 138-entry
# JSON file. The same discipline oracle/baseline.txt applies to mismatches.
#
# One id per line. `#` starts a comment. Corpus order.

# W2 TASK 5 -- the date/time batch, fourteen. Every one of these is an
# exception Kestra actually throws; none of them is a filter this task could
# not finish. The pairing is in error-class-pairs.txt and is asserted.
#
# Eight of the fourteen are the JAVA PATTERN COMPILER refusing a pattern, and
# they are the reason this task did not need a `RenderLimits`-style bound of
# its own: `DateTimeFormatter.ofPattern` caps every repeatable letter itself
# (`d` at 2, `S` at 9, `y` at 19), so a pattern of ten thousand letters is an
# IllegalArgumentException in Kestra and in egret rather than an allocation.
# `runners::javafmt` reproduces each message word for word.
#
#   filter-date-pattern-too-many-letters   -> date_reproduces_javas_pattern_letter_limits
#   filter-date-pattern-fraction-too-wide  -> date_reproduces_javas_pattern_letter_limits
#   filter-date-pattern-year-too-wide      -> date_reproduces_javas_pattern_letter_limits
#   filter-date-pattern-unclosed-literal   -> date_reproduces_javas_pattern_syntax_errors
#   filter-date-pattern-reserved-char      -> date_reproduces_javas_pattern_syntax_errors
#   filter-date-pattern-unmatched-bracket  -> date_reproduces_javas_pattern_syntax_errors
#   filter-date-unknown-named-format       -> an_unknown_format_name_is_compiled_as_a_pattern
#   filter-date-input-not-a-string         -> date_rejects_an_input_that_is_not_a_string
#   filter-date-input-unparseable          -> date_refuses_an_unparseable_input
#   filter-date-unknown-zone               -> date_refuses_an_unknown_time_zone
#   filter-dateadd-unit-lowercase          -> date_add_refuses_a_unit_that_is_not_a_chrono_unit
#   filter-dateadd-missing-unit            -> date_add_refuses_a_missing_unit
#   filter-dateadd-amount-not-a-number     -> date_add_refuses_an_amount_that_is_not_a_number
#   filter-dateadd-amount-not-numeric-text -> date_add_refuses_an_amount_that_is_not_a_number
#
# `filter-date-unknown-named-format` is the sharpest of them: `date('nope_format')`
# is NOT an unknown-format error at all. `AbstractDate.formatter` falls through
# both of its maps to `ofPattern(name)`, so the name is compiled as a PATTERN
# and the message names the first letter of it that is not a pattern letter --
# `Unknown pattern letter: o`.

# W2 TASK 5 FIX ROUND 1 -- nine more, every one of them a variant ONE STEP
# from an entry above that already passed. That is the pattern the fix round's
# review named, and it is what the probe sweep (every ASCII letter at counts
# 1-11, every ChronoUnit at ten magnitudes, 50 zone ids, 30 existingFormat
# patterns) exists to break: the entries above were chosen, unconsciously, to
# be the variants that pass.
#
# Two of these carry a FOURTH JDK sentence the earlier eight never reached --
# `Wrong number of pattern letters`, which is what `v` and `B` say for a count
# outside their non-contiguous sets (`v` takes 1 or 4; `B` takes 1, 4 or 5).
# `Too many pattern letters` is a different rule and was the only one pinned.
#
#   filter-date-pattern-generic-zone-wrong-count    -> date_reproduces_javas_pattern_letter_limits
#   filter-date-pattern-day-period-wrong-count      -> date_reproduces_javas_pattern_letter_limits

#   filter-date-pattern-pad-not-followed-by-a-letter-> date_reproduces_javas_padding_rules

#
# `filter-date-pattern-pad-at-a-wide-value` is the sharpest: it is the SAME
# pattern as the passing `filter-date-pattern-pad`, at a different clock time.
# 05:07 fits inside both pads; 10:30 does not, and Java throws

# the set is closed, checked by feeding all 597 `chrono-tz` names to
# `ZoneId.of`.
