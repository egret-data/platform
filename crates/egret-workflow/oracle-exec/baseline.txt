# The W3a execution oracle's ratchet baseline: the golden entries egret does not
# reproduce yet.
#
# tests/executor.rs fails if an id NOT listed here mismatches (a regression), and
# ALSO fails if an id listed here now MATCHES -- delete the line in the same
# commit that earns it. That second direction is what makes this a ratchet
# rather than a suppression list: a task cannot make progress without shrinking
# this file, and cannot claim progress it did not make.
#
# One id per line. `#` starts a comment. golden.json order.
#
# Written by W3a Task 2 at 294 entries, which is EVERY comparable golden entry.
# `advance()` and `build_plan()` are stubs, so each of the 266 `runs` entries
# produces an execution that never leaves [CREATED] with no runs at all, and
# each of the 28 `refused` entries is over-accepted. That is the starting debt,
# stated rather than estimated; Tasks 3-8 each bank their flowable's slice and
# drive it to zero.
#
# Task 3 (`sequential`) banked 101, leaving 193. Task 4 (`parallel`, `dag`)
# banked 4, leaving 189: `valids/parallel`, `valids/parallel-nested`, and the
# two `invalids` `Dag` refusals egret used to OVER-ACCEPT --
# `dag-cyclicdependency` and `dag-notexist-task`, which are the two checks
# Kestra's own `DagTaskValidator` makes.
#
# `valids/dag` is NOT banked and Task 4 could not bank it. Its runs, histories
# and attempts are reproduced exactly; one ordered pair is not, and cannot be by
# anything without a clock. See `oracle-exec/runnable.txt`, `The one ordered
# pair Task 4 could not reach`.
#
# Task 5 (`if`, `switch`) banked 8, leaving 181.
#
# Task 6 (`loop`, `Command::SpawnExecution`) banked 2, leaving 179 --
# `valids/loop-empty` and `valids/loop-null`, the only two `Loop` entries whose
# golden carries NO sub-execution. That is the whole of what this task could
# bank, and the reason is a hole rather than a gap in the implementation:
# nothing executes `Command::SpawnExecution` until W3b/W6, so egret's side of
# `spawned` stays empty and every one of the 41 golden entries that carries a
# sub-execution mismatches on that field alone. 33 of those 41 now differ on
# NOTHING ELSE -- derived by
# `tests/executor.rs::the_spawned_field_is_all_that_stands_between_these_
# entries_and_a_bank`, which fails if that number moves. See
# `oracle-exec/README.md`, `What Task 6 had to change, and what it banked`.
#
# Task 7 (`retry`, `errors:`) banked 16, leaving 163. Nine are retry
# (`retry-expo`, `retry-fail`, `retry-failed`, `retry-failed-flow-attempts`,
# `retry-failed-task-attempts`, `retry-flowable`, `retry-flowable-child`,
# `retry-flowable-nested-child`, `retry-random`) and seven are `errors:`
# (`change-state-errors`, `errors`, `replay-sequential-with-error-handler`,
# `restart_always_failed`, `restart_local_errors`, `sequential-with-global-errors`,
# `sequential-with-local-errors`).
#
# The `spawned` hole is now **38 of 41**, not 33: the four
# `retry-new-execution-*` entries reproduce every run, history and attempt
# Kestra recorded and differ only on the REPLACEMENT execution a
# `CREATE_NEW_EXECUTION` retry starts -- which nothing in `Command` can ask for
# and `ExecutionState` has no field for. `valids/retry-flowable-parallel` is the
# fifth, and it is the same hole with a `Loop` in front of it.
#
# `timeout:` is NOT among the lines this task deleted and never could have been:
# in this artifact the WORKER enforces it
# (`WorkerTaskCallable.java:61`), and Kestra's own validator refuses it on any
# non-`RunnableTask` (`FlowService.java:574`). It belongs to W4.
#
# Task 8 (the `invalids`) banked 14, leaving 149. Seven needed no new rule:
# `build_plan` called `spec::parse` and never `spec::validate`, so egret had two
# answers to "is this flow acceptable" and publish had been refusing seven of
# these flows since W1. The largest single cause of the over-acceptance was a
# missing CALL, not a missing rule. The seven that did need one are
# `duplicate-key` (the same key twice in one YAML mapping, caught at parse),
# `workingdirectory-invalid`, the two `scheduled-missing-inputs-defaults`,
# `inputs-validation`, and the two dashed-reference flows.
#
# **This paragraph did not exist until the final review**, and its absence is
# the symptom this file was named for in the plan: every task deletes lines from
# a file no single task owns, so the header narrative stopped at Task 7 while
# the line count kept moving. It said "leaving 163" over a file holding 149.
#
# The final review (`disabled:`) banked 4, leaving 145: `disable-simple`,
# `disable-error`, `sequential-with-disabled` and `if-with-only-disabled-tasks`.
# A disabled task now gets no `PlanTask` at all, which is Kestra's own rule --
# `Execution.removeDisabled` over `tasks`, `errors` and `finally` -- and until
# then egret CREATED AND RAN a task the author had disabled, flipping the
# execution's terminal state on four of the six flows that use the flag. Those
# four were filed here as "does not reproduce yet"; they were over-acceptances,
# and this file is not where an over-acceptance belongs. The other two are
# `disable-flowable` (held by the sub-execution hole alone) and
# `parallel-disabled-tasks` (held by one ordered pair, like `dag` and `if`).
#
# The null-list fix (`fix(workflow): a null task list is an empty one, as it is
# in Kestra`) banks 1, leaving 144: `valids/switch-impossible`. It was never a
# gap in the executor -- W1's bare `Vec<Task>` refused its `defaults: null` at
# PARSE, so `build_plan` never reached a trace to compare. It is the one
# OVER-REFUSAL the ratchet could see, and like the four `disabled:` entries
# above it is a line that should never have been here: an over-refusal is a
# divergence this programme forbids, not a trace egret does not reproduce yet.
#
# A panic, and a state machine that will not settle inside the step bound, are
# NOT covered by this file. A line here means "egret does not reproduce this
# trace yet"; it never means "egret may crash here". A line here also never
# means "egret over-accepts this flow": an over-acceptance is a divergence this
# programme forbids shipping, and the five that remain are named in
# `tests/executor.rs`'s `STILL_OVER_ACCEPTED` with an owner each, not here.
# W3b Task 5 (the oracle re-pointed at the REAL driver) banks 16 and loses 16,
# leaving 144. The two halves are separate events and this file records both,
# because a net figure would hide the whole of what the step cost.
#
# **Banked (16), and every one is attributable.** **SIXTEEN** are the
# sub-execution hole closing, not fifteen: this paragraph said `Fifteen` above a
# list of sixteen names, and W3b Task 5's own report said `fifteen ... and one
# needed only the render surface`. Neither is right, and the fact that settles it
# is derived rather than argued -- ALL SIXTEEN carry a `spawned`, and
# `the_sub_executions_are_compared_and_this_is_what_they_cost` prints and asserts
# exactly those names as the entries with a `spawned` that match. None banked on
# the render surface alone. `tests/executor.rs` now drives
# `worker::start_execution` and `worker::tick` instead of a harness, so
# `Command::SpawnExecution` is executed by `worker::spawn` (W3b Task 4) and
# `Trace::spawned` is populated --
# `flowable-with-parent-fail`, `loop-expression-context`, `loop-failed`,
# `loop-failed-no-transmit`, `loop-flowable`, `loop-map`, `loop-multiple`,
# `loop-nested`, `loop-parallel-equal`, `loop-parallel-less`,
# `loop-parallel-more`, `loop-parallel-unlimited`, `loop-serial`,
# `loop-serial-multiple-tasks`, `loop-switch`, `switch-in-concurrent-loop`.
# **FIVE** of those additionally needed the widened render surface, not four:
# this paragraph named four and Task 5's report named five, and the report's list
# is the right one -- `loop-map` reads `{{item.key}}`, `loop-nested`
# `{{item.parent.index}}` and `{{item.parents[1].value}}`,
# `loop-expression-context` reads the PARENT execution's
# `{{outputs.before.value}}` from inside a sub-execution, and BOTH `loop-switch`
# and `switch-in-concurrent-loop` render a `Switch` inside one.
#
# **Lost (16), and the cause of each is named.** These are entries the harness
# reproduced by FEEDING a terminal state out of `golden.json`; the driver runs a
# handler instead, so where egret has no handler or renders differently from
# Kestra, the entry stops matching. W3b Task 1 measured 11 of them in advance
# and named them individually; five more were invisible to that derivation
# because a fed terminal hides everything the task would have DONE.
#
#   the 11 Task 1 predicted -- a task type W3b writes no handler for, so
#   `Registry::run` refuses it, the tick aborts for that run and the execution
#   stalls: `core.output.OutputValues` on `assert`, `flow-with-array-outputs`,
#   `output-values`, `replay`, `webhook-outputs`, `webhook-wait`;
#   `core.log.PurgeLogs` on the five `purge_logs_*`; `core.execution.Assert`
#   also on `assert`.
#
#   `errors` -- the `errorLogs()` function, which W2 refuses by name and
#   assigns to W3 (`runners::functions::REFUSED`); egret has no task-log store
#   for it to read (W3b Task 3's Concern 7).
#   `variables` -- the `render()` function, refused by W2 and assigned to W3 in
#   the same table. Not implemented here; named rather than absorbed.
#   `webhook-plaintext` -- `{{ trigger.parameters… ?? 'hello-world' }}`. egret's
#   `??` resolves a missing MEMBER (`outputs.not_existing ?? ''` renders) and
#   not a missing ROOT, so the fallback is never reached. A W2 divergence the
#   fed terminal used to hide.
#   `restart-child` -- `{{ 1 / taskrun.attemptsCount }}` with `attemptsCount`
#   0 on the first attempt. Java throws `ArithmeticException: / by zero` and the
#   run FAILED; minijinja divides as floats and renders `Infinity`, so egret
#   SUCCEEDS and runs one more task. Also W2, also hidden by the feed.
#   `parallel-fail-with-flowable` -- Kestra FAILED a `Sleep` that was still in
#   flight when its sibling failed the `Parallel`. W4 Task 3 wired
#   `TaskHandler::cancel`, and deliberately not to this seam: the kill path
#   fires on a task's own `timeout:` expiring, which is the artifact's only
#   `kill(null)` site, whereas a run a FLOWABLE abandoned is `advance()`'s
#   decision and `advance()` has no worker to tell. So egret still completes it,
#   and this entry does not move.
#
# `valids/dag`, `valids/if`, `valids/parallel-disabled-tasks` and `valids/full`
# are the four entries that now differ on the happens-before relation ALONE --
# runs, attempts and execution history byte-identical to Kestra's. The cause is
# this driver's delivery discipline: it finishes ONE task run per tick and
# creates that run's successors in the same transaction, where Kestra's worker
# pool finished two siblings before either successor existed. It is NOT the
# guard W3a deleted; see
# `the_guard_w3a_deleted_did_not_come_back_and_the_reason_is_the_transaction`.
# `valids/full` reaching this list settles W3b Task 1's Concern 3, which said
# its attribution was wrong and its real cause unknown.
#
# The whole-branch review's fix round banks 1 more, leaving 143:
# `valids/replay-loop`. It is a `Loop` whose body reads `{{ inputs.* }}`, and the
# cause is a seam rather than a construct: W3b Task 4 wrote `worker::spawn`'s
# INSERT and W3b Task 5 added `executions.inputs` (migration 0136), so a
# sub-execution was created without its parent's inputs and 0136's
# `DEFAULT '{}'` applied. `render::Surface::load` reads `inputs` for the CURRENT
# execution only -- unlike `outputs`, which walks the parent chain -- so a loop
# body branched on the declared default instead of on what was posted. No test
# in `tests/worker.rs` could reach it: every fixture there builds its flows with
# no `inputs:`. `a_sub_execution_inherits_the_posted_inputs_of_its_parent` is
# the property, and it asserts the `else` branch, because a body taking the
# `then` would pass with the column missing.
#
# The same fix moves `valids/finally-loop` and `valids/finally-loop-parallel`
# from `differs on more` into `differs only INSIDE spawned` -- they are the two
# entries whose loop body is an `If` on `{{ inputs.failed == false }}` with
# `true` posted and `false` declared, i.e. the two that named the defect. They
# stay baselined for `finally:`, which has no owner.
