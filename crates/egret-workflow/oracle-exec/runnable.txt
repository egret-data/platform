    left:  ["dag","task1","task2","task3","task4","task5","task6"]
    right: ["dag","task1","task2","task3","task4","task6","task5"]

So the gap the plan's Step 4 asked about -- "the corpus has no dag flow with a

`valids/dag` is STILL BASELINED, and no state machine without a clock can bank

  pair (3, 4) = (task3, task4)     golden: before      egret: overlapping

worse implementation, not a fix: it makes one slow branch block an independent
short branch's successor, which is observable and wrong.

What the caller can render, and what that costs (W3a Task 5)
------------------------------------------------------------

`advance()` is pure and cannot render, so `tests/executor.rs` gained a tier that
does: it renders an `If`'s `condition` or a `Switch`'s `value` with egret's own
W2 renderer, over a context of

  inputs  the values `corpus.json` records `harvest.py` as having POSTED for the
          very execution the golden was captured from, plus the flow's own
          declared `defaults:` for every input the harvest did not post
  vars    the flow's own `variables:` block

and nothing else.  Kestra's `RunContext` reaches far more -- task outputs, the
loop `item`, `execution`, `taskrun`, `trigger`, `labels`, the KV store -- so an
expression over any of those cannot be resolved here, and an unresolvable
expression FAILS the run.

The cost is DERIVED rather than argued, by
`the_caller_can_render_every_branch_expression_except_the_two_kestra_could_not`:
over every planned `If` and `Switch` in the comparable corpus there are 26
expressions, 24 render, and the 2 that do not are

  valids/if-condition-fail   `{{ inputs.run }}`      (no such input declared)
  valids/variables-invalid   `{{inputs.invalid}}`    (no such input declared)

which are exactly the two the ARTIFACT could not render either -- the test reads
each failing task's own run out of `golden.json` and requires it to end FAILED.
Both entries are banked BY that path.  A third failure, on a task Kestra ran to
SUCCESS, would be an entry egret gets wrong because of the harness rather than
because of `advance()`, and that assertion is what would surface it.

The `defaults:` half of the context is worth its own line, because leaving it
out was a real defect and not a simplification.  Five entries post `inputs: {}`
and declare their input with a `defaults:` -- `valids/exit`,
`valids/exit-cancelled`, `valids/exit-killed`, `valids/exit-nested` (two `If`s)
and `valids/parallel-fail-with-flowable` (two `If`s), SEVEN expressions between
them.  Kestra fills those defaults before it renders anything; without that step
all seven failed to render too and their `If`s were FAILED for a reason that had
nothing to do with the flow.  7 + 2 = 9 of the 26 failed before the filling
step; 2 fail after it.  `valids/parallel-fail-with-flowable` -- the flow Task 4's whole
`fail_the_rest` rule was argued from -- banks BECAUSE the defaults are applied.

One entry is still mismatching for a reason the context cannot fix, and it is
not the renderer's fault: `valids/if-with-only-disabled-tasks` renders
`{{ vars.numeric_variable > 0 }}` to "true" correctly, and mismatches because its
`then` holds a `disabled: true` task, which no W3a task claims.


W3a Task 5 fix round 1: three things round 0 stated wrongly
------------------------------------------------------------

1. THE TRIM.  `is_truthy` transliterated Kestra's `condition.trim()` to Rust's
   `rendered.trim()`, and they are not the same function.  Java strips code
   units <= U+0020; Rust strips Unicode `White_Space`.  Neither set contains the
   other.  18 more literal-condition flows were published and executed on rc13,
   and 11 of them DISAGREE with `str::trim()`:

     Java trims, Rust does not (Kestra `else`, egret gave `then`):
       U+0001 + "false" + U+0001,  U+000E + "false" + U+000E,
       U+001F + "false" + U+001F,  U+0001 + "0" + U+0001
     Rust trims, Java does not (Kestra `then`, egret gave `else`):
       U+00A0 (NBSP) + "false" + U+00A0,  U+0085 + "false" + U+0085,
       U+3000 + "false" + U+3000,  U+2007 + "false" + U+2007,
       U+2028 + "false" + U+2028,  U+00A0 + "0" + U+00A0,  U+00A0 alone

   U+000B and U+000C are in BOTH sets and agree, which is why a smaller probe
   would have missed it -- and so did the original 20 rows, because every padded
   one of them pads with an ASCII space.  The predicate is now
   `trim_matches(|c| c <= '\u{20}')`, the committed rows are 38, and the test
   asserts the SET of 11 disagreeing rows by name so a revert to `.trim()` fails
   there.  Nothing in the corpus reaches it; an NBSP in a rendered value is not
   exotic, which is why it is fixed rather than recorded.

A fourth null-versus-empty gap, measured and NOT closed
-------------------------------------------------------

A `Switch` with a `value` and NO `cases` key publishes and its run FAILS; the
same flow with `cases: {}` runs `defaults` to SUCCESS.  Both measured live.
W1's `models::Switch::cases` is a bare `BTreeMap`, so absent and `{}` arrive
identically and egret runs `defaults` for both -- right for `{}`, wrong for
absent.  Implementing the absent spelling would break the explicit one, so it is
recorded rather than fixed.  It is the same model gap as `defaults: null` vs
`defaults: []`, in the sibling field; whoever closes one closes both.  No corpus
flow is either shape.
