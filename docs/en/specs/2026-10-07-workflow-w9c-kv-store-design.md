**Decided with the user, 2026-10-07:**
- **(2026-10-07) Scope.** W9c ships the `kv()` function; the tasks `Set`, `Get`, `GetKeys` and `Delete`; `PurgeKV`; the deep-merge `Put` task; and the KV API. The plugin host gets **no** KV bridge, because no catalog plugin calls `namespaceKv`. Its refusal message changes to point at the `core.kv.*` tasks (§10).
- **(2026-10-07) The write scope is W9b's.** A flow reads the KV of any namespace in its workspace. It writes and deletes only in its own namespace. `PurgeKV` acts on the flow's own namespace and its child namespaces, on a dot boundary. One `authorize` serves both W9b and W9c, with a KV resource kind added. Kestra lets a flow write any existing namespace; §2 records the divergence (§5).
- **(2026-10-07) Storage follows Kestra.** Each revision's value is an Ion text object at `{prefix}{ws}/{ns-as-path}/_kv/{key}.ion`, or `….ion.vN` for revision N > 1. A Postgres table, `workflow.kv_entries`, holds one row per revision: workspace, namespace, key, revision, type, size, description, `expires_at`, deleted, `created_at` and `created_by` (user, execution or task run). egret **stores** the type, where Kestra re-infers it on read; the Task 1 fixture decides whether read results still match Kestra, and every measured difference is a row in §2. A write reuses W9b's staging. The body is staged while no connection or lock is held. Then one short locked transaction locks `(ws, ns, key)`, checks `overwrite`, picks the revision, copies server-side, runs `head`, inserts the row and commits. So `overwrite: false` and `Put`'s read-merge-write are race-free. A value is capped by `max_file_bytes`; Kestra has no cap (§2). *(Amended 2026-10-07 by the user's ruling on the value cap, below: the cap is `max_read_bytes`.)* Keys follow Kestra's regex `[a-zA-Z0-9][a-zA-Z0-9._-]*`, and their length is bounded (§3). The migration takes the next free number on main: 0175 today, re-checked by the plan's rebase step (§3, §4).
- **(2026-10-07) TTL: expired means missing.** A read of an expired key behaves exactly like a read of a missing key, and it honours `errorOnMissing`. Reads never write. An hourly sweep hard-deletes expired keys, rows and objects, by row id, across every workspace, and it is safe to run on every replica. Kestra soft-deletes on read, errors regardless of `errorOnMissing`, and sweeps only the `main` tenant and namespaces that have flows (§2, §4.5, §11).
- **(2026-10-07) Inheritance follows Kestra.** A `kv()` with no namespace, or a `Get` whose namespace is the flow's own, walks up the parent namespaces on a dot boundary. An explicit namespace does not walk. The API has a list-inherited route (§4.6, §9).
- **(2026-10-07) `secret()` inside a `Set` or `Put` value is refused at publish.** The error says the secret's value would be exposed through the KV store. This diverges from Kestra (§2, §7).
- **(2026-10-07, the user's ruling on the value cap) A KV value's writes are capped at `max_read_bytes`, not `max_file_bytes`, so anything writable is also readable.** `Set`, `Put` (its merged result included) and the API's `PUT` refuse an encoded value over `max_read_bytes`, naming the cap (§2, §4.2, §4.3, §8.1, §8.5, §9).
- **(2026-10-07) Approved design points (sections 2–4 of the brainstorm).**
  - Versions and soft delete follow W9b's R1. Every write makes a new revision. `Delete` flags the latest revision. History is visible through the API, with deleted revisions flagged. A rewrite after a delete makes a new revision.
  - `PurgeKV` purges expired keys only, or by version (`before` / `keepAmount`). It filters with `keyPattern` and deletes by row id with keyset paging. W9b's rule applies: a version purge needs `keepAmount` or `before`.
  - `Set` takes `key`, `value`, `overwrite` (default true), `ttl`, `kvType` and `kvDescription`. BOOLEAN is strict, as in the artifact.
  - `Get` outputs `value`. `GetKeys` takes `prefix`, lists live keys only, and is bounded by `max_namespace_files`. `Delete` outputs `deleted`. `Put` deep-merges under the key's lock, with merge semantics measured in Task 1.
  - `kv()` uses W9b's per-render connection and `authorize(Read)`. Its `errorOnMissing` defaults to true; the tasks' defaults to false.
  - The API lives under `/api/ws/{ws}/workflows/namespaces/{ns}/kv…`. It has list, list inherited, get (with type), revisions, put (through staging, with a body bound and timeouts), delete and bulk delete. Reads need `workflow:read` and writes `workflow:manage`. A lock wait over 5 s answers 409. Statuses follow W9b's conventions.
  - The plan's shape (§12) and the testing approach (§13), with W9b's lessons as global constraints.
- **(2026-10-07, the user's rulings on the plan's gaps)**
  - **Bulk delete.** The API's bulk `DELETE` takes at most **1,000 keys per request**. It stays one all-or-nothing transaction. A body over the cap answers 413 naming it (§9). One advisory lock per key, in one transaction, at `max_namespace_files` keys could exhaust Postgres's shared lock table (`max_locks_per_transaction` × `max_connections`, about 6 400 slots on a stock server).
  - **Server-paced store calls under the key's lock are accepted.** These are `Put`'s bounded read and write, the copy and `head` of `Set` and the API's `PUT`, and the object deletes of `PurgeKV` and the expiry sweep. Client-paced I/O under a lock (a request body), a render and a plugin run stay forbidden. API writers keep the 5 s lock wait, then 409 (§4.3, §15).
  - **`Put` on an expired key treats it as missing.** It starts fresh and carries over no description and no expiry (§4.5, §8.5).
  - **A namespace of another workspace** answers exactly as an empty namespace. The listings answer `200 []`; a key read and `revisions` answer 404 (§9, §13).
  - **Decisions recorded from the plan:**
    - a key named `inheritance` cannot be read by `GET …/kv/{key}`, as in Kestra (§9, §15); *(Clarified 2026-10-08, Task 6 fix round 1, review M3: the path `…/kv/inheritance` answers the listing; the key is still reachable as `…/kv/inheritanc%65`, see §9, §15.)*
    - the expiry sweep's first pass comes one interval after start (`interval_at`; §11);
    - `PurgeKV` re-reads and judges a key's rows under the key's session lock (§8.6);
    - no second latest-row index (§4.1);
    - the audit's spelling (§9).
- **(2026-10-07, the user's rulings on Task 1's findings)**
  - **(2026-10-07) `Put` stays a real deep merge.** On the artifact a flow's `value` reaches `Put` as JSON text and is stored as a STRING, so `Put.mergeValues` is unreachable from a flow. egret merges the typed value, with the semantics the artifact's own `Put.mergeValues` computes (the fixture's `put_merge` cells). §2 records the divergence (§8.5).
  - **(2026-10-07) The API's `PUT` body: one Ion value, or the raw text.** A body that parses as exactly one Ion value is stored as that value's type. Anything else (two or more values, or text that is not Ion) is stored whole as the raw text, typed STRING. A value of a type the KV store does not model (a blob, a clob, an s-expression) is refused with 400 naming the type. A timestamp with a time is a DATETIME, in UTC, whatever its offset or hour; a day-precision timestamp is a DATE. Kestra's 500 for a timestamp without an offset becomes the raw text (§2, §4.2, §9).
  - **(2026-10-07) `PurgeKV`'s `before` follows Kestra.** A revision is purged when it stopped being the latest (the `created_at` of the key's next revision) at or before `before`. The latest revision is never purged by `before`, a soft-deleted latest included (§2, §8.6).
- **(2026-10-07, the user's rulings on Task 1's review)**
  - **(2026-10-07) R-a: `Set` stores a YAML map or list typed, as `Put` keeps it.** A `Set` whose `value` is a YAML map or list stores it as JSON, each string leaf rendered by the typed render (`{{ 1 + 1 }}` is the number 2), and a YAML number or boolean keeps its type; `kv()` then returns the map. On the artifact `value` is a string property, so the leaves render as strings and the whole value is stored as a STRING of its JSON text. One render rule serves `Set` and `Put` (§2, §8.1, §8.5).
  - **(2026-10-07) R-b: an empty `PUT` body is 400.** A 0-byte body, or one holding only whitespace (no Ion value at all), answers 400 "empty body", and nothing is written (§9).
  - **(2026-10-07) R-c: a year- or month-precision Ion timestamp is the raw text.** `2025T` and `2025-01T` are stored as the raw text, typed STRING: such a value is neither an instant nor a date (§2, §9).
- **(2026-10-07, the user's ruling on Task 2's review)**
  - **(2026-10-07) Decimals are preserved exactly.** A number that arrives as an Ion decimal (only the API's `PUT` makes one) stays a decimal through every read, merge and write, and no digit is lost (every number has at most 1,000 digits, by the ruling below; a longer one is refused, never truncated). A float stays a float, and an integer stays an integer, at any size. A flow's value keeps `serde_json`'s semantics: a JSON number with a fraction or an exponent is a float, as Kestra's Jackson makes it a `Double`. A reader (`kv()`, `Get`, the API) sees a decimal as its exact plain digits, as `BigDecimal.toPlainString` writes them; no Task 1 cell measures how Kestra prints a decimal it read, so the plain form is egret's choice (§2, §4.2). *(Clarified 2026-10-08, Task 8: "plain" means no exponent; it does not mean the scale is kept. A decimal is stored with the trailing zeros after its point dropped (§4.2, Encoding), so `1.50` reads back as `1.5`, where `BigDecimal.toPlainString` of `1.50` would print `1.50`. The value and every significant digit are kept; the scale is not. Measured by `api.put_bodies.dec_150` and by Task 8's end to end, which read `1.50` and `1.500d0` back as `1.5`.)* *(Fixed 2026-10-08, final review F1, the user's ruling: until then the "every read, merge and write" above did not hold for a write a flow rendered. `Set` and `Put` read their typed render back from `toJson`'s text, so `Set {value: "{{ kv('price') }}"}` stored a 31-digit decimal as the float `1.2345678901234568e29`. The typed render now converts the value it evaluated straight to KV data: an exact decimal or big integer keeps its kind and every digit, top level or nested in a list or map. A flow's own literal is unchanged: `{{ 1.5 }}` and a YAML `1.5` are floats (§8.1, §15).)*
  - **(2026-10-07) The dense-value limit.** A KV value may hold at most one Ion value per 64 bytes of `max_read_bytes` (163,840 values at the 10 MiB default; about 320 KB of small numbers), counting the value itself and every value nested in it. A write over the limit is refused, naming the limit; nothing is stored. The limit is the Ion reader's value budget, which bounds the memory a read takes, so anything writable stays readable (§4.2, §15).
- **(2026-10-07, the user's ruling on Task 2's re-review 2)**
  - **(2026-10-07) Every number in a KV value has at most 1,000 digits.** Integers, decimals and floats all count. A decimal counts the digits of its coefficient, written in plain notation as egret stores it; in binary Ion the length field is counted. A longer number is refused with an error naming the limit (413 on the API), never truncated. The limit is enforced before the Ion parser sees the number, on every write (a flow's value, `Put`'s merged result, the API's body) and every read (§2, §4.2, §15).

- **(2026-10-07, the user's ruling on Task 3's review)**
  - **(2026-10-07) Conflicting dotted keys in a `Put` are refused.** When one keyed entry's dotted path is a leaf that another entry of the same patch also sets or writes inside (`[{key: q.r, …}, {key: q, …}]`, `[{key: a.b, …}, {key: a, value: {z: 1}}]`, `a` and `a.`), the patch is refused with an author error naming both keys. Kestra nests the entries in its `HashMap`'s iteration order, so its outcome depends on hash order, not on the entries. Patches without such a conflict keep the artifact's semantics (§2, §8.5).
- **(2026-10-07, the user's ruling on Task 3's re-review)**
  - **(2026-10-07) Both `Put` limits are accepted.** A keyed entry's dotted key has at most 100 segments (`storage::ion::MAX_DEPTH`), and a patch at most `max_read_bytes / 64` dotted segments in all (163,840 at the default). A deeper key is an author error naming the limit; a larger patch is refused before the key's lock, as a 413-class error naming the limit. Kestra merges any; the second limit can refuse a patch whose keys share long prefixes although its merged value would be stored (§2, §8.5, §15).
- **(2026-10-07 and 2026-10-08, the user's rulings on Task 4's review, I1)**
  - **(2026-10-07) Comparisons on exact numbers compare exactly.** A `BigDecimal` or `BigInteger` that `kv()` returns (a stored decimal, or an integer beyond `u128`), or that `number(type='BIGDECIMAL')` returns, compares by its value under `==`, `!=`, `<`, `<=`, `>`, `>=`, `in`, `not in` and a chained comparison: against an int, a float or another exact number; `1.5 == 1.50` is true; negatives order correctly; `kv('d') in [1.5]` is true; `sort` orders them by value. Arithmetic stays a named refusal (the earlier ruling, §15). Before this, minijinja ranked the object above every number and compared two of them as text, so `kv('threshold') > 0.9` was always true and `== 0.75` always false, silently (§2, §6, §15).
  - **(2026-10-08) Option A: the comparison operators are compiled into calls.** minijinja cannot compare its object against a number (`Ord for Value` compares the value's kind first; `Object::custom_cmp` is consulted only between two objects of one type), so a second rewriter pass reads the rewriter's output with minijinja's own grammar and turns every comparison into a call (`a > b` → `kestra_gt(a, b)`). The call compares exactly when an exact number meets a number, and otherwise answers with minijinja's own `PartialEq`/`Ord` after the same undefined checks, so every other comparison keeps its answer and its error text; a differential test holds it to that, and the expression oracle moved by exactly the one entry this fixes (§6).
  - **(2026-10-08) A float is compared by its exact binary value.** `0.1` the float is `0.1000000000000000055511151231257827…`, so a stored decimal `0.1` is less than it and not equal to it (§15).
- **(2026-10-08, the user's ruling on Task 5's review)**
  - **(2026-10-08) egret's renderer keeps float division.** `{{ 7 / 2 }}` is `3.5`, so `Set` stores the float `3.5e0`, where Pebble divides two integers as integers and stores `3` (w9c `typed_render.tr_div`, now chosen, Pebble's `3` under `kestra`). This is a renderer gap, not the KV store's: every egret render divides as floats. A renderer-wide fix is a follow-up after W9c (§2, §15).

## 2. What Kestra does, and where egret differs

## 3. Storage layout and keys

- **Object key:** `{workflow.storage.prefix}{workspace_id}/{ns-as-path}/_kv/{key}.ion` for revision 1, `…/{key}.ion.v{N}` for N > 1 (Kestra's `kvFileName`). Same bucket and prefix as W9a and W9b. The workspace always comes from the grant (§5), never from input. `FileStore` gains `namespace_kv_uri(grant, key, revision)` beside `namespace_object_uri`. **No URI names a KV value:** a flow reaches a value only through `kv()` and the tasks, so `storage::uri` is unchanged.
- **The `_kv` segment rule.** A namespace whose segment is `_kv` (`a._kv`, legal by `is_valid_namespace`) would put its flows' execution keys and its namespace files under namespace `a`'s KV prefix. `access::check_namespace` gains the clause beside `_files` (a `check_kv_segment`), so `authorize` refuses such a namespace for every KV and every namespace-file operation, and publish refuses it as it refuses `_files`, each with an error naming the namespace and the segment. Task 1 counts the published flows in a dev database and the corpus entries whose namespace has a `_kv` segment, and lists each; none is expected.
- **The key rule**, one function (`kv::key::check_key`) for every entry point (function, tasks, API): Kestra's regex `^[a-zA-Z0-9][a-zA-Z0-9._-]*$` (`KVStore.java:137`) and at most **350 bytes**. Kestra's messages for an empty key and a key that breaks the regex are reproduced as Task 1 measures them; the length refusal names the bound. **Why 350:** it is Kestra's own column width (`kv_metadata.name VARCHAR(350)`), so every key Kestra can hold, egret can hold. The key is ASCII by the regex, so bytes equal characters. A key never holds `/`, so it is one object-key segment, and it never starts with `_`, so no key can be named like a marker.
- **The key budget.** After the prefix, a KV object key holds at most 36 (workspace) + 1 + 150 (namespace) + 1 + 3 (`_kv`) + 1 + 350 (key) + 4 (`.ion`) + 12 (`.v` and a revision) = 558 bytes. W9b's boot rule (a prefix of at most 200 bytes) therefore keeps every KV key under S3's 1024 bytes too; no new check is needed.
- **Staging** reuses W9b's: a value's encoded bytes go to `{prefix}{ws}/_nsfiles_staging/{uuid}`, recorded in `workflow.namespace_file_staging` (`staging::record`, `forget`), and swept by the existing hourly sweep (`spawn_staging_sweeper`). The table and the segment keep their W9b names.

## 4. Core

### 4.1 The metadata table

- `id bigserial` primary key; `workspace_id uuid` FK to the workspace, `ON DELETE CASCADE`; `namespace text`; `key text` (the key rule as a CHECK: length ≤ 350 and the regex); `revision int` (≥ 1).

- `deleted bool` default false; `deleted_at timestamptz` and `deleted_by_user`, `deleted_by_execution`, `deleted_by_task_run` (nullable, set together with `deleted`).
- `created_at timestamptz` default `now()`; `created_by_user`, `created_by_execution`, `created_by_task_run` with W9b's one-writer CHECK (`CreatedBy::{User, Execution, TaskRun}`).
- `UNIQUE (workspace_id, namespace, key, revision)`, whose index also serves the latest row; a partial index on `expires_at` where `expires_at IS NOT NULL` for the sweep. *(2026-10-07, the user's ruling: the unique constraint's index leads with `(workspace_id, namespace, key)` and is scanned backwards for the latest row, as W9b's is. The `deleted_by_*` columns are beyond the column list the user named: they let a `Delete` re-claimed after an outage recognise its own earlier delete (§8.4, §11). **A KV value exists only once its row exists.** The latest row of a key is its highest revision; that row is the key's state.

### 4.3 Writing

Every write (`Set`, `Put`, the API's `PUT`) has this shape. W9b's lesson holds: **no database connection and no lock is held across a caller-paced body.**

1. **Check** the key (§3), the namespace and the write rule (§5) through `authorize(…, Resource::Kv, Access::Write)`, then render and type the value (a task, §8.1) or parse it (the API, §9). Encode it (§4.2) and check its size against `max_read_bytes`, before anything is staged.
2. **Stage.** Record a staging row (`staging::record`) and put the encoded bytes to its staging object, holding no connection and no lock.
3. **Commit**, on a detached task as W9b's `commit_staged`, so a dropped request or a cancelled future still finishes. In one transaction:
   - take `pg_advisory_xact_lock(hashtextextended('w9c:{ws}:{ns}:{key}', 0))`, under `SET LOCAL lock_timeout` when the grant has a `lock_wait` (the API's 5 s; a flow waits as long as it takes);
   - read the latest row;
   - apply the re-claim skip: when this task run already wrote the latest revision (`created_by_task_run`), answer "already written" and write nothing (§11);
   - apply `overwrite: false`: a live, unexpired latest row is a conflict naming the key; a missing, soft-deleted or expired one is not;
   - set `revision = max + 1` (1 for a new key);
   - copy the staging object onto the revision's key server-side (`ObjectStore::copy`);
   - `head` it, whose size must be the staged size;
   - insert the row;
   - commit.
4. **Forget** the staging object and its row on every way out (written, skipped, refused, failed).

`Put` skips step 2 and differs in step 3: it reads, merges and writes under the lock (§8.5). A `Delete` takes the same lock and updates the latest row (§4.4). The lock serialises every writer of one key, and the window it covers is server-paced: one server-side copy, or `Put`'s bounded read and write. *(2026-10-07, the user's ruling.)* These server-paced store calls under the key's lock are **accepted**:
- `Put`'s read and write, each at most `max_read_bytes`;
- the copy and `head` of `Set` and the API's `PUT`;
- the object deletes of `PurgeKV` and the sweep, under the session lock.

Client-paced I/O under a lock stays forbidden: a request body is read and staged before any lock (§9). An API writer still waits at most 5 s for the lock, then answers 409.

### 4.4 Revisions and soft delete

Following W9b's R1:
- Every write makes a new revision; earlier revisions and their objects stay.
- `Delete` flags the latest revision `deleted` (with `deleted_at` and `deleted_by_*`), under the key's lock. No revision is added, as in Kestra.
- A latest read of a soft-deleted key is missing. An explicit-revision read (`GET …/kv/{key}?revision=N`) of a soft-deleted key's revision succeeds, unless that revision has expired (§4.5).
- `GET …/kv/{key}/revisions` lists every revision, deleted ones flagged.
- A write after a delete makes revision `max + 1`, live.
- Revisions and their objects stay until `PurgeKV` or the expiry sweep removes them.

### 4.5 Reading and expiry

- **Live** means the latest row is not deleted and `expires_at` is null or later than the database's `now()`. Every latest read (`kv()`, `Get`, `GetKeys`, the API's list, get and inheritance) answers only from live rows.
- **Expired means missing.** An expired key reads exactly as a key that was never written: `kv()` and `Get` honour `errorOnMissing`, `GetKeys` and the listings leave it out, `Set` with `overwrite: false` may write over it. An explicit-revision read of an expired revision is not-found too.
- **Reads never write.** Nothing on a read path inserts, updates or deletes; the sweep (§11) and `PurgeKV` remove expired keys.
- **Expiry is fixed at write:** `expires_at = created_at + ttl`, both one `clock_timestamp()` read by the database under the key's lock (Task 3 review I4: `now()`, the transaction's start, is before the lock wait, so a writer that waited longer than its ttl would be born expired). The writers judge a latest row's expiry at `clock_timestamp()` too. A ttl is at most 1,000 years (365,250 days); a longer one is the author's error naming `ttl` (Task 3 review I3). A ttl of zero is accepted from the API's header (expired at once) and refused by the `Set` task (`parse_ttl`'s two modes, w9c `api.headers.h_ttl_zero`, `ttl.PT0S`). `Put` keeps the latest revision's `expires_at` and description (Kestra, `Put.java:121`) when that revision is live. An expired key is missing to `Put` as to every reader: `Put` starts fresh, with no description and no expiry (§8.5; the user's ruling, 2026-10-07).
- A read resolves the latest live row, then reads that revision's object (bounded by `max_read_bytes`, §4.2). **A missing object behind a row is an author error naming the key and the revision**, with no fallback (W9b's rule). An unreachable store or database is an infrastructure error (§11).

### 4.6 Inheritance

- `kv(key)` with no `namespace`, and `Get` whose rendered `namespace` equals the running flow's own, look the key up in the flow's namespace and then in each parent, cutting at dots (`a.b.c` → `a.b` → `a`), and answer from the first namespace where the key is live. An expired or soft-deleted key at a level is missing there, and the walk goes on.
- An explicit `kv(key, namespace)` does not walk, even when the namespace is the flow's own (`KvFunction.java:64-66`). `Get` with any other namespace does not walk. `GetKeys`, `Delete`, `Set`, `Put` never walk.
- The walk reads each level through `authorize(Read)`, which any namespace of the workspace passes. One query reads every level's latest row (at most the namespace's segment count, ≤ 75); one object is read.
- When no level has the key, the missing-key message names the namespace Kestra's message names, which Task 1 measures; egret reproduces it.

### 4.7 One access function

W9b's `nsfiles::access::authorize` gains a resource kind: `authorize(workspace, actor, target, resource: Resource::{NamespaceFiles, Kv}, access)`. The rule is the same for both kinds (§5); the resource changes only the refusal's words ("namespace files" or "the KV store"), and the `Grant` records it. Every KV store function takes a `Grant` and asserts its resource and access (`require`), so a namespace-file grant cannot reach KV and a Read grant cannot write. *(2026-10-08, final review F4: one direction only. W9b's namespace-file reads call no `require`, so a KV grant an egret bug handed one would read namespace files; nothing is gained, since the Read rule is the same for both resources.)* The access rule stays in one module, `nsfiles::access`, for both packages.

## 5. Who may read and write

- **Workspace:** always the running execution's (for the API, the route's `{ws}` after the permission check). Nothing in a property or argument names a workspace.
- **Read** (`kv()`, `Get`, `GetKeys`, the inheritance walk): any namespace of the workspace. A namespace with no KV simply has no keys.
- **Write** (`Set`, `Put`, `Delete`): the running flow's own namespace only, compared exactly.
- **Purge** (`PurgeKV`): the flow's own namespace and its child namespaces (`ns == own`, or `ns` starts with `own + "."`).
- **API:** any namespace of the route's workspace, after `workflow:read` (reads) or `workflow:manage` (writes) (§9).
- A refusal is an author error naming the namespace and the rule; it never says whether a key exists there. Each refusal has a test that fails when it is removed.

## 7. Secrets in KV values

- **At publish**, a `Set` or `Put` whose `value` calls `secret(…)` anywhere in its templates is refused with a new code, `secret_in_kv_value`. The message names the task and the property and says: *the secret's value would be stored in the KV store, where anyone who can read this namespace's KV (`workflow:read`) could read it, unmasked; pass the secret to the task that needs it instead.* It is reported **instead of** the generic `CODE_SECRET_OUTSIDE_PLUGIN_TASK` for that property, so the author reads the reason that applies.
- The scan is publish's existing `secret()` scan (`spec/validate.rs:395-403`), pointed at the two tasks' `value`. The refusal stands on its own: it holds even if `secret()` is later allowed outside `kestra.*` tasks.
- The API's `PUT` is unaffected: its body is a literal value the caller already holds.
- A value that reaches a secret indirectly (a variable or an output that holds one) is not detectable at publish. At run, `secret()` is still confined (`SECRET_REFUSAL`), so no `secret()` call renders in a KV task. *(Reworded 2026-10-08, Task 4 review M5.)* That does not keep a secret out of a KV value: a `kestra.*` plugin task resolves `secret()` in its own properties, its outputs can carry the resolved value, and a later `Set` whose `value` is `{{ outputs.p.x }}` stores it unmasked. The publish scan blocks only a literal `secret()` call in the value.

### 8.5 `Put`

- `key`, `value` (any type), `namespace` (write rule), `errorOnMissing` (default false). `value` is rendered by §8.1's one render rule, so a YAML map reaches the merge as a map.
- **The merge rules** follow the artifact (`Put.java:72-121`): a map deep-merges into a map; a list of `{key, value}` entries patches dotted paths; a single `[{value}]` entry replaces the whole value. The exact semantics are **measured in Task 1** and pinned by fixture cells: nested maps, arrays inside maps, a type clash between a map and a scalar, a missing key with each `errorOnMissing`, and a dotted path through a missing level. egret implements against the fixture.
- *(Measured 2026-10-07, Task 1: on the artifact a flow's `value` reaches `Put` as JSON text, so `Put` stores a STRING and never merges (§2). The fixture's merge semantics come from the artifact's `Put.mergeValues`, run on typed values. Maps merge recursively. A list inside a map is appended to. A null in the patch leaves the field as it was. A scalar replaces a map, and a map a scalar. A dotted entry builds missing levels and replaces a scalar on its path. A keyed entry over a non-map value fails with ``Cannot apply keyed `value` updates to a non-JSON existing KV value.`` Ruled 2026-10-07 by the user: egret merges, and §2 records the divergence.)*
- *(The user's ruling, 2026-10-07, Task 3 review I2: keyed entries whose dotted paths conflict, one a leaf that another sets or writes inside, are refused naming both keys; on Kestra the result depends on hash order.)*
- *(The user's ruling, 2026-10-07, on Task 3's re-review: the merge's bounds.)* A keyed entry's dotted path is at most `storage::ion::MAX_DEPTH` (100) segments. A deeper one is an author error naming the limit, refused before anything is built: the merged value could not nest deeper and still be read. A patch's segments **in all** are at most the dense-value limit, `max_read_bytes / 64` (163,840 at the default), refused before the key's lock is taken, as a 413-class error naming the limit. Why that bound: the merge is linear in the segments, so it bounds the work under the lock whatever the patch's size, and each segment the nesting builds is at least three of the tokens the read-back counts against the same limit (a name, a colon, a value or a brace), so a patch over it whose paths share no prefix could only make a value over the limit anyway. Only a patch whose many keys share long prefixes is refused where its merged value would be stored. Before this bound, a 50,000-segment key took 88 s under the lock and then overflowed a 2 MiB stack as it was dropped, aborting the process.
- **Under the key's lock.** `Put` runs §4.3 step 1 for its patch and stages nothing, since the merged bytes exist only under the lock. Then, in the commit transaction, holding the lock:
  - read the latest live row, and its object (bounded by `max_read_bytes`). A key that was never written, is soft-deleted or has **expired** is missing: `errorOnMissing` decides, and a write starts fresh (the user's ruling, 2026-10-07; §4.5);
  - merge;
  - check the merged result's encoded size against `max_read_bytes`: a larger result fails the task, naming the cap, and nothing is written;
  - write the merged object directly to the revision's key;
  - `head` it;
  - insert the row, keeping the latest live revision's description and `expires_at` (a missing key carries over neither), with the type of the merged value;
  - commit.

  The lock covers one bounded, server-paced store read and one store write, never a caller's body.
- **Why the merge runs under the lock** rather than optimistically outside it: with a retry loop, a busy key would fail a flow for another writer's timing, which W9b rules out for flows. The re-claim skip applies as for `Set`. Output: none.

### 8.6 `PurgeKV`

- **Namespaces:** `namespaces` xor `namespacePattern` (Kestra's wildcard grammar, W9b's `glob` Commons-IO matcher); the default is the flow's own namespace. `includeChildNamespaces` defaults to true, matches on a dot boundary, and applies to `namespaces` (and the default) only: a `namespacePattern` names its namespaces itself, and its matches are never expanded to their children, as in Kestra's `PurgeTask.findNamespaces` *(2026-10-07, Task 1 review I4; `purge.namespaces.namespacePattern_exact` purges `w9c.pp` alone)*. The candidates are only the namespaces holding KV that are the flow's own or its children, so a pattern never reaches another namespace. A listed namespace outside the purge rule is refused by name before anything is purged. At most 64 namespaces are listed or covered (W9b's `MAX_NAMESPACES`).
- **`keyPattern`:** the same wildcard grammar, on the key.
- **`behavior`:**
  - `{type: key, expiredOnly: true}` (the default) purges every revision of each matched key whose latest revision has expired.
  - `{type: key, expiredOnly: false}` is refused. The error names `behavior: {type: version, keepAmount: 0}` as the form that purges every revision.
  - `{type: version, keepAmount, before}` keeps the `keepAmount` highest revisions of each matched key, or, with `before`, purges each revision that **stopped being the latest at or before `before`**: the revision whose next revision of the same key has a `created_at` at or before `before`. The latest revision has no next one, so `before` never purges it. With `keepAmount` a soft-deleted key is purged entirely (W9b's rule); with `before` a soft-deleted key keeps its latest (deleted) revision, as on Kestra. `keepAmount: 0` purges every revision. *(The user's ruling, 2026-10-07: `before` follows Kestra, which compares the row's `updated` column, the time it stopped being the latest. This replaces "revisions created at or before `before`". Measured: `purge.version_before`.)* A `version` behaviour with neither property is refused, naming both and saying that `keepAmount: 0` purges everything.
  - *(Measured 2026-10-07, Task 1: Kestra refuses `before` together with `keepAmount` (`behavior: Cannot set both 'before' and 'keepAmount' properties`), and egret refuses it too. A version purge with neither property purges every revision on Kestra.)*
- **Execution, as W9b's `PurgeFiles`:**
  - Rows are read in keyset pages of `max_namespace_files + 1` by `(key, revision)`.
  - Each page's complete keys are purged per key, under the key's session lock (`LockedSession`). *(2026-10-07, the user's ruling.)* Under that lock the key's rows are **re-read and judged as they are then**, as the sweep does (§11), so a key rewritten since the listing is judged on its new rows. Each purge deletes the rows by id, commits, then deletes the objects, then unlocks. The lock is still held when the objects are deleted, so a writer cannot reuse a freed revision number's object key in between.
  - A key holding more revisions than the cap fails the task, naming it, with the keys before it purged.
  - The purge runs to completion on a detached task.
- **Output** `{size}`: the count Kestra reports, revisions or keys, **measured in Task 1**. *(Measured 2026-10-07, Task 1: revisions, not keys.)*

## 9. The KV API

Under `/api/ws/{ws}/workflows/namespaces/{ns}/kv`, mirroring `KVController`, with W9b's route conventions (`WsContext`, then `egret_core::authz::require` with `WF_READ` or `WF_MANAGE`, then `authorize(…, Actor::Api, …)`; `no_store()` answers 503 when `[storage]` is absent; each write emits one audit mutation; no new permission). *(2026-10-07, the user's ruling on the audit's spelling, W9b's form.)* The action is `workflow_namespace_kv:{put|delete|delete_many}` and the resource type `workflow_namespace_kv`. The resource id is `{ns}/{key}`, or `{ns}` for a bulk delete, which lists the keys in its detail.

| route | permission | answer |
|---|---|---|
| `GET …/kv` | `workflow:read` | the namespace's live keys, each with `key`, `type`, `size`, `description`, `expiresAt`, `revision`, `updated`; at most `max_namespace_files`, else 413 |
| `GET …/kv/inheritance` | `workflow:read` | the ancestors' live keys only, deepest first, the first occurrence of a key winning (Kestra, `:73-100`), each with its namespace; the same bound |
| `GET …/kv/{key}?revision` | `workflow:read` | `{type, value, revision, updated, description, expiresAt}`, the value typed (§4.2); a latest read of a missing, soft-deleted or expired key is 404; a given `revision` of a soft-deleted key is served, an expired one is 404 (§4.4, §4.5) |
| `GET …/kv/{key}/revisions` | `workflow:read` | every revision: `revision`, `type`, `size`, `description`, `expiresAt`, `created`, `deleted`, `expired`; 404 when the key has no row |
| `PUT …/kv/{key}` | `workflow:manage` | body `text/plain`: exactly one Ion value is stored as that value's type, anything else as the raw text, typed STRING; an empty or whitespace-only body is 400 "empty body"; a year- or month-precision timestamp (`2025T`, `2025-01T`) is the raw text, STRING; a single Ion value containing a blob, clob or s-expression at any depth is 400 naming the type, even under an annotation, while a body of several values is the raw text whatever they hold (the user's rulings, 2026-10-07; 2026-10-08, review M7; Kestra, `:124-141`, keeps the first value of a stream); headers `description` and `ttl` (ISO-8601); always overwrites; §4.3; 200 with no body |
| `DELETE …/kv/{key}` | `workflow:manage` | §4.4; `true` when a live key was deleted, `false` when there was none (200 either way) |
| `DELETE …/kv` | `workflow:manage` | body `{keys: […]}`, at most **1,000** keys (the user's ruling, 2026-10-07; more is 413 naming the cap); one transaction taking each key's lock in ascending order, all or nothing; `{keys: […]}` lists the keys that were live and are now deleted |

- **The `PUT` body** is bounded by `max_read_bytes` (it is parsed in memory to type it, §4.2), and so is the encoded value (the user's ruling, 2026-10-07). It is read with W9b's body timeouts: no byte for 30 seconds, or more than 12 hours in all, answers 408 and writes nothing. The body is read and staged before any lock is taken.
- *(Measured 2026-10-07, Task 1: Kestra keeps the first value of an Ion stream, so `hello world` is stored as `"hello"`. A timestamp at exactly midnight UTC is stored as a DATE. The fixture's `api` cells record the rest.)*
- **The `PUT` body's type** *(the user's ruling, 2026-10-07)*. One principle: a body that parses as **exactly one** Ion value is stored as that value's type; anything else is the raw text, typed STRING.
  - An empty body, or one holding only whitespace, is no value at all: 400 "empty body", nothing written *(the user's ruling R-b, 2026-10-07)*.
  - Two or more values (`hello world`, `1 2`, `PT1.5S`), or text that is not Ion (`{a:`, a timestamp with a time and no offset, which Ion's grammar does not allow), is stored whole as the raw text. The raw-text fallback never infers a type: `PT1.5S` is a STRING.
  - A blob, a clob or an s-expression, at any depth of the value, is a type the KV store does not model. The `PUT` is refused with 400 naming the type, and nothing is written.
  - A timestamp with a time is a DATETIME, converted to UTC at millisecond precision, whatever its offset and even at midnight UTC. A day-precision timestamp is a DATE. A year- or month-precision timestamp (`2025T`, `2025-01T`) is the raw text, typed STRING *(the user's ruling R-c, 2026-10-07)*.
  - Whitespace around the one value is not a second value (`  42  ` is NUMBER 42). An annotated value (`x::1`), at any depth (`{a:x::1}`), makes the whole body the raw text, as Kestra keeps `x::1`.
  - **Precedence** *(2026-10-07, Task 1 re-review N3; reworded 2026-10-08, Task 6 fix round 1, review M7)*: the refusal comes first. A single Ion value containing a blob, clob or s-expression at any depth is refused with 400 naming the type, even when an annotation would otherwise make it raw text (`x::{{aGVsbG8=}}` is 400 `blob`).
  - *(2026-10-08, Task 6 fix round 1, review M7.)* **A body of several values is the raw text, whatever they hold.** How reading stops decides first: a second value (`Stop::Full`) or text that stops being Ion (`Stop::Failed`) makes the whole body the raw text, typed STRING, before any value is looked at. So `1 {{aGVsbG8=}}`, `(a b) 1` and `{{aGVsbG8=}} {a:` are each stored as a STRING, and the refusal above applies only to a body that is one Ion value.
  - *(2026-10-08, final review F5.)* **The digit limit applies only to a body that is one Ion value.** The digit scan refuses a long number before the reader can see that a second value follows or that the text stops being Ion, so a text body refused that way that holds a run of more than 1,000 digits is read once more with each such run as one digit. When that is not one Ion value, the body is the raw text, typed STRING (`note 111…`, `111… note`, `{a:111…`); when it is one, the 413 stands (`[1, 111….5]`).   - *(2026-10-08, Task 6 fix round 1, review M6.)* A timestamp with a time whose offset carries it outside the years 1-9999 once converted to UTC (`0001-01-01T00:00+01:00` is year 0 there, `9999-12-31T23:59:59-01:00` year 10000) is refused with 400 "the timestamp … is in year … in UTC, outside the years 1-9999 a DATETIME can hold", naming it; nothing is written.

## 11. Lifecycle and failure classification

- **The expiry sweep.** Every egret process with a store starts `spawn_kv_expiry_sweeper` beside W9b's staging sweeper. It runs hourly, the first pass after an hour, over every workspace. *(2026-10-07, the user's ruling.)* It uses `interval_at(now + every, every)`, not `interval`, whose first tick is immediate (W9b's staging sweeper uses `interval`):
  - It lists, in keyset pages of 1000 by row id, the keys whose latest row has `expires_at <= now()` (the partial index).
  - For each key, it takes the key's session lock with `pg_try_advisory_lock` and skips the key when it is busy; the next pass retries.
  - Under the lock it re-reads the latest row. If that row is still expired, it deletes the key's rows by the ids it read, commits, deletes the objects, then unlocks.
  - A key rewritten in between keeps its new revision.
  - Two replicas sweeping at once are harmless: a busy key is skipped, and a delete by id of a row already gone is a no-op.
  - A failed object delete is logged; its row is already gone, so the object is orphaned (§15).
  - Age is the database's clock.
- **Re-claims are idempotent.** After an infrastructure failure the same task run is re-claimed.
  - `Set` and `Put` skip when this task run wrote the latest revision (`created_by_task_run`, judged under the key's lock, §4.3), so a retry adds no revision and `overwrite: false` never conflicts with its own write.
  - `Delete` answers `deleted: true` when this task run deleted the latest revision (§8.4).
  - `PurgeKV` recomputes from the rows as they are; its `size` counts what the re-claim purged itself.
  - The skip keys on the task run, so it also covers a `RETRY_FAILED_TASK` retry, as W9b's does.
  - **The residue (Task 3 review M6).** The skip keys on the latest row, so a re-claim acts again over another writer's later change, as W9b's does: when another writer deleted the key after the first attempt's `Set`, the re-claimed `Set` writes it again; when another writer rewrote the key after the first attempt's `Delete`, the re-claimed `Delete` deletes that newer value. An own write that has since expired is still "already written" (rewriting would extend its life past what the first attempt gave); once the sweep removed it, a re-claim writes again.
- **`kv()` inside `settle`'s transaction** *(2026-10-08, Task 4 fix round 1, review M3)*. A `kv()` in a `runIf`, an `If` condition or a `Switch` value renders inside `settle`'s transaction, so that transaction's pool connection and its row locks are held across the call. The window, per `kv()` call: the render's namespace connect, the first time the render looks anything up (34 ms measured cold, bounded only by the OS's TCP timeout, §15); one lookup statement; one object download of at most `max_read_bytes` (10 MiB) and its decode; and, only when the object is not the size its row records, one more statement and one store `head`. The number of calls in one condition is bounded by the render's fuel, and the time by the store client's and the OS's timeouts, not by egret. `kv()` takes no lock and opens no transaction of its own. The window is inherited, not new: W9a's `read()` and W9b's file functions render in the same place (W9b §6 accepts it), and a slow store read in a `runIf` holds `settle`'s row locks for its duration.
- **A flow's write waits** for a busy key as long as it takes (W9b's rule): what it waits behind is server-paced, either one copy or one `Put`'s bounded read and write. An API write waits 5 s (§9).
- **Failure classification** (KV reuses W9b's `NsError` and its split):

| failure | class | effect |
|---|---|---|
| the key rule, a refused namespace, a write-scope refusal, a malformed `ttl`, a failed `kvType` coercion, a `Put` shape the merge refuses, `expiredOnly: false`, a `version` purge with neither property, a cap crossed (`max_read_bytes`, `max_namespace_files`, 64 namespaces), `overwrite: false` over a live key, missing with `errorOnMissing: true`, a missing object behind a row | author (`Author`, `NotFound`, `Conflict`, `TooLarge`) | the task fails with a message naming the key, the namespace or the cap; the API answers 4xx |
| `secret()` in a `Set`/`Put` value | author, at publish | the flow is not published (§7) |
| the store or the database unreachable, at run or at render | infrastructure (`Store`, `Db`) | the handler returns `Err`, or the render sets `infrastructure_failure`; the run is re-claimed with no attempt spent; the API answers 503 |

No error names a secret, a storage key or another workspace.

## 15. Known limits

- A flow writes and deletes only its own namespace's KV; a Kestra flow that `Set`s another namespace's key fails on egret, naming the namespace (§5).
- `PurgeKV` with no `namespaces` purges the flow's own namespace and its children, not every namespace; `expiredOnly: false` is refused in favour of `version` with `keepAmount: 0` (§8.6).
- `secret()` in a `Set` or `Put` value is refused at publish (§7).
- A KV value is at most `max_read_bytes` (10 MiB by default), where Kestra has no cap; a `Set`, `Put` or API `PUT` of a larger value fails, naming the cap (§4.2; the user's ruling, 2026-10-07).
- A KV value holds at most `max_read_bytes`/64 values (163,840 at the default); a denser value is refused at write, naming the limit (§4.2; the user's ruling, 2026-10-07).
- Every number in a KV value has at most 1,000 digits (an int's digits, a decimal's coefficient in plain notation, a float's mantissa, an exponent); a longer one is refused at write, naming the limit, where Kestra's own bound is not measured. A decimal such as `1d1000`, whose Ion coefficient is one digit but which egret writes as 1,001 digits, is refused too, on read and on write (§4.2; the user's ruling, 2026-10-07).
- Arithmetic on an exact decimal, or on an integer beyond `i128`, that `kv()` returns fails the render as the author's error (a named refusal, never a silent conversion to a float), where Kestra's Pebble computes it in `BigDecimal`; an integer within `i128` and a float compute as before (§6; Task 4).
- A comparison on an exact decimal or big integer is exact (the user's ruling, 2026-10-07, I1). An exact number against a float compares against the float's exact binary value (2026-10-08), where Pebble 4.1.2 compares any two numbers by `doubleValue()`: so a stored decimal `0.1` is not `== 0.1` and is `< 0.1` here, and equal in Kestra; and two decimals that differ past the 17th significant digit differ here and are equal in Kestra. `isIn` compares `toString()`s, as Kestra's `InExpression` does, so `kv('d') isIn [1.5]` is true for a stored `1.5` and false for `1.50` (§6).
- Every comparison operator in a template is compiled into a call to egret's comparison functions (§6). A chained comparison (`a < b < c`, minijinja's; Pebble has none) evaluates all its operands before comparing, so an operand whose evaluation fails (`nothere.x`) fails the render even after an earlier comparison was false, where minijinja stopped at the false one; an operand that is merely undefined is still not checked past a false. *(2026-10-08, Task 4 cleanup N3: an operand here includes a `kv()` call. `{{ 1 > 2 > kv('missing') }}` performs the lookup, and fails the render under `kv()`'s default `errorOnMissing: true`, where minijinja stopped at the false.)*
- *(2026-10-08, Task 4 cleanup N2.)* Names starting with `kestra_` are reserved: they name the functions egret's rewriters call (`kestra_gt`, `kestra_is_in`, `kestra_null_coalesce`, …), and a template variable of that name would shadow one. A `set`, `for` or `with` that assigns such a name fails the render at compile time with "`kestra_gt` cannot be assigned: names starting with `kestra_` are reserved for egret's own functions". Pebble has no such names, so a Kestra flow is not expected to hit it.
- Pebble's `is null` test is not bound by egret's renderer (a renderer gap, oracle entry `null-literal-is-null-test`, not the KV store's): `{{ kv('x', errorOnMissing=false) is null }}`, Kestra's idiom for a missing key, fails the render with "unknown test". Write `== null`, or `??` for a default (fixture cell `kv_function.missing_eom_false_is_null`; Task 4 review M1).
- *(2026-10-08, Task 5; the user's ruling, 2026-10-08.)* `Set`'s typed render evaluates with egret's renderer, which divides two integers as floats: `{{ 7 / 2 }}` stores `3.5`, where Pebble stores `3`. The user kept egret's float division: w9c `typed_render.tr_div` is chosen, egret's `3.5e0` at its top level and Pebble's `3` under `kestra`. This is a renderer gap, not the KV store's: every render divides that way. A renderer-wide fix is a follow-up after W9c.
- *(2026-10-08, final review F1.)* `Set`'s and `Put`'s typed render keeps an exact number exact, except in a value holding a string that is itself a template (`{{ [x, '{{ y }}'] }}`): the renderer's next pass evaluates that string inside the value's JSON text, the text no longer matches what the expression evaluated, and it is read back as JSON, as before F1, so an exact decimal in that same value becomes a float (§8.1).
- `Get`'s `outputs.value` keeps a decimal's exact digits in the stored output JSON, but a later render of `outputs.get.value` reads that JSON as an `f64`, so the digits a reader sees there are the double's; only `kv()` hands a template the exact value (§8.2).
- A decimal is written with the trailing zeros after its point dropped (`1.50` → `1.5`, `200.00` → `200.`, `0.000` → `0.`). Only `1.50` → `1.5` is measured (`api.put_bodies.dec_150`); the rest is extrapolated from that cell, not measured (§4.2).
- DATETIME, DATE and DURATION values come back as strings in egret's renders, so a template comparing them compares strings (§4.2).
- The read-increment-`Set` pattern (`retry-with-flowable-errors`) is racy, as in Kestra; `Put` is the race-free form for a map, and there is no atomic increment.
- An expired key keeps its rows and objects until the next sweep, up to about an hour; reads already treat it as missing (§4.5).
- The sweep's failed object delete leaves an orphaned object, which nothing lists afterwards, as W9a's and W9b's purges do.
- Deleting a workspace cascades its `workflow.kv_entries` rows away and leaves its `_kv` objects in storage, as W9b's namespace files are left.
- At render, every database error of a `kv()` lookup is an outage, re-claimed with no attempt spent, and a lookup is bounded only by the OS's TCP timeout; this is W9b's render limit, shared (W9b §15).
- A namespace with a `_kv` segment is refused (§3).
- A ttl is at most 1,000 years (365,250 days); a longer one is refused naming `ttl` (§4.5; Task 3 review I3).
- At most two bulk deletes of one process hold their (up to 1,000) key locks at once; a third waits for a permit, holding no connection. Across replicas the advisory lock table is still shared: about seven concurrent 1,000-key bulk deletes on different replicas could fill a stock server's ~6,400-slot lock table (§9; Task 3 review M2).
- A conflicting dotted-key `Put` patch is refused where Kestra answers by hash order (§8.5; the user's ruling, 2026-10-07).
- A `Put` key of more than 100 dotted segments is refused, and so is a patch of more than `max_read_bytes / 64` dotted segments in all (163,840 at the default), where Kestra merges any. The second can refuse a patch whose keys share long prefixes although its merged value would be stored (§8.5; the user's ruling, 2026-10-07).
- *(2026-10-08, Task 5 fix round 1.)* A `Put` patch, its keyed-entry wrapper included, nests at most 100 deep (`storage::ion::MAX_DEPTH`): a flow's patch goes through `render_value`, which bounds every flow value at 100 (its literal leaves by `KvData::from_json`'s rule), before Task 3's `put_merge` (which itself allows `MAX_DEPTH + 2`). So a keyed entry's value nests at most 98 deep. A deeper patch is the author's error, even when the merged value (at most 100 deep) could have been stored (§8.5).
- An object that is not the size its row records, under a row that has not changed, is an author error naming the key and revision, not retried, as a missing object is; a retry would read it again. A row that changed while it was read (a purge and a rewrite reused the revision) is retried (§4.5; Task 3 re-review 1, 2026-10-07).
- An API bulk delete waits for one of its process's two permits at most its 5 s lock wait, then answers 409; a flow's waits as long as its key locks do (§9; Task 3 re-review 1, 2026-10-07).
- `GET …/kv/inheritance` is the inheritance listing, as in Kestra, so a key named `inheritance` is not read by that path. It is read with any letter of its name percent-encoded (`GET …/kv/inheritanc%65`), since the route is matched on the path as sent and the key decoded afterwards. Its write, delete and revisions routes work, and so do the tasks and `kv()` (§9; the user's ruling, 2026-10-07; corrected 2026-10-08, Task 6 fix round 1, review M3, which found the encoded read).
- The API's bulk delete takes at most 1,000 keys per request (413 past it); a larger set takes several requests, each all or nothing (§9; the user's ruling, 2026-10-07).
- Server-paced store calls run under a key's lock, and a writer of that key waits behind them:
  - `Put`'s bounded read and write;
  - the copy and `head` of `Set` and the API's `PUT`;
  - `PurgeKV`'s and the sweep's object deletes.

  A flow waits as long as it takes; an API writer waits 5 s, then gets 409. Accepted by the user's ruling, 2026-10-07 (§4.3).
- *(2026-10-08, final review F6.)* A flow writer (`Set`, `Put`, `Delete`) waiting for a busy key holds a pool connection while it waits: its transaction begins before it takes the key's lock, and a flow's lock wait is unbounded. N writers queued on one hot key (a `ForEach` that `Put`s into one shared map) hold N connections, so with the default `database.max_connections = 10`, ten of them pin the process's pool and the executor and the API wait until the queue drains. W9b's namespace-file writes have the same shape. A lock taken without holding a connection while it waits (a try-lock with backoff) is a follow-up.
