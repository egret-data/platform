## 1. Problem

Three things a stored flow declares are parsed, saved and never run:

1. **A `Loop`'s `outputs:` and `fetchType:`.** Kestra evaluates the outputs once per iteration, at the end of that iteration's sub-execution, and collects them into a list on the `Loop` run (`{{ outputs.loop.outputs }}`). egret models neither key (`EW src/models/task.rs:534-559`), warns `not_honoured` naming #6 (`EW src/spec/keys.rs:167`), and writes no outputs at all on a `Loop` run, so `{{ outputs.loop.outputs }}` is undefined and fails under the strict renderer.
2. **A `Loop`'s `retry:`.** Kestra gives a failed task inside an iteration the nearest ancestor's `retry:`, walking the parent flow's task tree up through the `Loop` (`KX ExecutorService.java:576-599`, `:841-856`). egret's `spawn::sub_flow_source` (`EW src/worker/spawn.rs:830-899`) drops the `Loop`'s `retry:` when it builds the iteration's flow, and `retry::policy_for` (`EW src/executor/retry.rs:156-190`) stops at the sub-execution's root. No warning says so.
3. **The flow-level `outputs:`.** Kestra evaluates them when the execution ends (`KX ExecutorService.java:441-477`), before `afterExecution:` runs, and a failure turns the execution `FAILED`. egret validates them (`EW src/spec/validate.rs:1088-1096`) and never evaluates them: `execution.outputs` is a constant `{}` (`EW src/worker/render.rs:279-284`), so is a `Subflow`'s `outputs.<sub>.outputs` (`EW src/worker/subflow.rs:774-779`), and `workflow.executions` has no `outputs` column. No warning says so.

Banks (attributions, measured by T0 and each task): **8** executor entries upper bound, 6 strict, from the post-merge **301 / 35 / 35 / 0** to **301 / 27 / 27 / 0** (strict **29 / 29**). Only `subflow-secret-output-child` and `-parent` stay among the entries this package touches. *Measured, 2026-10-29 (Task Z): **10** banked, **301 / 35 / 35 / 0 → 301 / 25 / 25 / 0**; the two `subflow-secret-output-*` entries banked too (Q3's correction below; §4, §7).*

- **Q2. `retry-flowable-parallel` is in #6.** A `Loop`'s own `retry:` (and an ancestor's) is inherited by the tasks of each iteration (D7).
- **Q3. SECRET outputs are encrypted with egret's key and masked everywhere**, as SECRET inputs are (KI-112, `EW src/secret_inputs.rs`; D9). `subflow-secret-output-child` and `-parent` stay baselined: Kestra fails them only because its oracle harness has no encryption key, a harness difference, not an egret gap. *Corrected 2026-10-29 (Tasks B1, B3, recorded by Task Z): both banked. The oracle's egret has no master key either, just like Kestra's harness, so egret refuses to store the SECRET output and the child ends `CREATED RUNNING SUCCESS FAILED` as in Kestra (B1), and the parent's `Subflow` run then fails as Kestra's `failSubflowDueToOutput` (B3). The decision itself stands: with a key, egret seals and masks the value (pinned by `tests/worker.rs`).*
- **Q4. A FILE-typed output, or a STORE URI, that names storage outside the execution's own storage is refused**, recorded as a security divergence (Kestra OSS checks nothing; D10, §6).
- **Q5. Accumulated `Loop` outputs are capped:** 1 MiB per iteration's map and 16 MiB for the whole list. Beyond either, the iteration fails with a message that points to `fetchType: STORE` (D4). Kestra has no cap; recorded as an egret-only limit (§6).

### 2.2 Corrections to the roadmap's premises

Measured in the survey (§1, §2, §7) and binding on this design:

1. **"A `Loop`'s `outputs:` evaluated at its end" is wrong.** They are evaluated **per iteration**, when each iteration's sub-execution ends (after its `errors:`/`finally:`), in that sub-execution's render context, and each result is appended to a list on the `Loop` run (survey §2 items 1, 5). There is no evaluation "at the end of the `Loop`".
2. **"STORE needs the W9a store" is stale.** W9a's internal storage and ION files exist; `loop-values-from-uri` already matches (a `Loop`'s `values:` read from a URI works). STORE needs only a write of one ION file per iteration (D5).
3. **"Banks: 3 (+ up to 4)" is wrong. The banks are 8:** 5 `Loop`-output entries (`loop-outputs`, `loop-outputs-failed-render`, `loop-outputs-store`, `loop-outputs-auto`, `if-in-parallel`; STORE and AUTO were reopened 2026-10-19), 1 retry entry (`retry-flowable-parallel`) and 2 flow-output entries (`after-execution`, `flow-with-outputs-failed`).
4. **The "4 unattributed `Loop` entries" are named, and none is a `Loop`-outputs cause:**
   - `if-in-flowable`: the `equals` operator, banked by #5a (Task A6);
   - `loop-object` and `loop-object-in-list`: the `json` test, banked by #5b (Task B2, PR #780);
   - `retry-flowable-parallel`: a `Loop`'s `retry:` not inherited by its iterations, **this package** (Q2, D7).
5. **Package #1 missed two silent drops.** Its "every parsed-but-ignored key warns" left no `not_honoured` warning for the flow-level `outputs:` or for a `Loop`'s `retry:`. `EW src/spec/schema/property-treatment.json` marks both "honoured" (`Flow.outputs` at `:17`, `Loop.retry` in the `Loop` row at `:557-575`) because that file measures the **save** path only (D8 fixes the honesty).
6. **The cause list's "flow `outputs:` … may be partly stale (inferred)" (roadmap `:296`) is not stale.** Nothing evaluates flow outputs anywhere.
7. **Stale code comments:** `EW src/worker/render.rs:8-11` (the surface gap is no longer why `loop-outputs-auto` cannot resolve its `values:`; W9a Task 11 closed that) and `EW src/models/task.rs:518-521` ("deliberately out … unused before W3").
8. **Measured by Task A1, 2026-10-29: "the save-time check flow outputs already have (each output has a `type`; ids unique; `validate.rs:1088-1096`)" (D8) is half wrong.** Those lines checked only `type`; nothing in egret refused duplicate flow-output ids. Kestra does, for the flow's list only (`FlowValidator.java:107-111`, `Duplicate output with name [...]`); it does not look inside a `Loop`'s `outputs:`. A1 therefore added the duplicate check for both lists (code `duplicate_output_id`, Kestra's text): on the flow it is Kestra's rule, on a `Loop` it is egret-only (a duplicate would make one output silently overwrite the other in the iteration's map). Where each check lives: `type` required runs in the run-time gate as the flow's already did (`loop_output_type_required`, beside `loop_values_required`); the duplicate check, the SECRET-under-STORE refusal (`loop_secret_output_stored`) and the new warning below are **save-only**, so a version stored before #6 (whose `Loop` outputs never ran) still starts. A5 must therefore also refuse a SECRET output under STORE at evaluation, for such a stored version.
9. **Measured by Task A1, 2026-10-29: a `CREATE_NEW_EXECUTION` retry that reaches a `Loop` iteration saved silently** (D7 asked A1 to check). It is the flow's, the `Loop`'s, an ancestor's, or a body task's own `retry:`, and `worker::replay` refuses it at run (the iteration ends FAILED, no new execution, as Kestra). A1 added a save-time `not_honoured` warning at that `retry:`'s `behavior`, naming the refusal, computed with D7's precedence (own > nearest ancestor through the `Loop` > flow), for runnable tasks and `Subflow` inside a `Loop`.
10. **Controller decision, 2026-10-29 (resource bound, recorded by Task B2): flow-level outputs are capped as `Loop` outputs are.** The typed map a flow's `outputs:` evaluate to may serialise to at most **16 MiB per execution** (`env::MAX_FLOW_OUTPUTS_BYTES`, the same value as the `Loop` list's total; the 1 MiB-per-iteration rule of D4 is `Loop`-only). Beyond it the evaluation fails at the terminal as a failing output does (`FAILED` appended, nothing stored, the line logged on the execution), with `Flow outputs are <n> bytes; egret keeps at most 16 MiB of flow outputs per execution. Write a large value to internal storage and declare it as a type: FILE output instead.` (a flow output has no `fetchType`, so the way out named is a FILE output). The size is the typed map's, SECRET values in clear; the message names sizes, never a value. Kestra has no cap; an egret-only limit (§6 item 3).
11. **Task B2, 2026-10-29: the SECRET flow outputs are revealed to the execution's own renders only.** `worker::render::Surface::load` reads `workflow.executions.outputs` and opens `secret_outputs` (D9); a Flow trigger's `when`/`inputs` are rendered over the SOURCE execution's surface (`execution_render_context`), and what they render becomes ANOTHER execution's inputs, so that context gets `execution.outputs` with the SECRET values masked (`Surface::hide_flow_secret_outputs`). D9's "a Flow trigger ... sees the mask" is thereby applied to `{{ execution.outputs }}` in the trigger's own render as well as to `trigger.outputs` (Task B3).
12. **Controller decision, 2026-10-29 (recorded by Task B3): a Flow trigger's render context hides every sealed output, and still reveals the SECRET inputs (a known pre-existing limit).** Task B2 masked `execution.outputs` there (item 11); B2 reported that the same context still revealed a `Loop` run's sealed SECRET outputs (Task A4's list) into renders whose result becomes another execution's inputs. Task B3 closes that: `Surface::hide_flow_secret_outputs` also puts back the stored (masked) form of every run output whose sealed values the surface revealed, a `Loop` run's list and a `Subflow` run's copy (item 13), own or inherited. **Not changed, recorded as a known limit:** the execution's SECRET **inputs** (KI-112, `secret_inputs::reveal`) are still revealed in that context, so `{{ inputs.pw }}` in a Flow trigger's `when`/`inputs` renders the value into the listener's execution. This predates package #6 and is left as it is by the controller's decision; closing it is a KI-112 follow-up.
13. **Task B3, 2026-10-29: the `Subflow` copy, `trigger.outputs` and the API, as built.**
    - **`Subflow` (`wait: true`).** `worker::subflow::on_child_terminal` copies the child's stored `outputs` (masked) onto the `Subflow` run as `outputs.<sub>.outputs`, and the child's sealed object, unchanged, into the run's `task_runs.secret_outputs`; the parent's render surface reveals it (the parent is the child's execution family, D9), and a Flow trigger's context over the parent masks it (item 12). A child that declares no `outputs:` gives `{}` as before. **A child whose declared outputs were not stored** (its evaluation failed, or it ended before `RUNNING`) fails the run as Kestra's `Subflow.failSubflowDueToOutput`: the child's state, then `FAILED` (or what `allowFailure:`/`allowWarning:` soften it to, `State.Type.fail`) appended once, ONE fresh attempt `[CREATED, <state>]` (the new `Command::FailSubflowOutputs`), no outputs, and an ERROR line `Failed to extract outputs with the error: '…'` on the run. Kestra re-renders the child's outputs in the parent; egret copies what the child's terminal stored, which is the same evaluation over the same surface, except for a child ended before running whose outputs are all literals (§6 item 7). This banks `valids/subflow-secret-output-parent` (re-attributed to B3 by Task B1).
    - **`trigger.outputs`.** A Flow trigger's `inputs:` render with `trigger: {outputs}` bound when the source's stored outputs are non-empty, as Kestra's `Flow.evaluate`, and with no `trigger` otherwise (W13a's measured "Unable to find `trigger`"); only `outputs` is bound, so `{{ trigger.executionId }}` still fails there. The fired execution's trigger record carries `variables.outputs` (omitted when there are none). For a `dependsOn` listener the outputs are Kestra's deep merge of the completing event's outputs with the window's, the window keeping its creator's outputs keyed `namespace -> flowId` (`FlowTriggerService.buildOutputs`; the `flow_trigger_windows.outputs` column of migration 0158, written NULL until now). SECRET values are the mask throughout. **Not built: `trigger` in the listener's own task renders.** `worker::render` binds no `trigger` root at all (its module doc lists it as not supplied, for every trigger type), so `{{ trigger.outputs.x }}` in a task of the fired flow still fails; binding `trigger` is a general render-surface change outside package #6.
    - **API.** `ExecutionRow`/`ExecutionListItemDto` carry `outputs` (the stored, masked map) on `GET` of an execution and on the list; `secret_outputs` is selected by no API statement. `openapi.json` and the frontend client (`npm run gen:api`) are regenerated; the field is optional in the client, so no screen changes. *Corrected 2026-10-30 (fix wave 6, final review I4): `outputs` is on the detail only (`ExecutionDetail`/`ExecutionDto`); the list leaves it out, since a row can carry 16 MiB.*
14. **Task B4, 2026-10-29: the SECRET and FILE surface, verified end to end, and the one gap closed.** Most of D9/D10 had been built ahead by A4, A5, B1–B3; B4 walked every path an output value or URI can take and pinned what was not yet pinned.
    - **SECRET, every path (verified).** Stored maps hold `******` and the sealed columns the values (`Loop` list, flow outputs, `Subflow` copy); only `worker::render::Surface::load` opens them; every log line and failure message after the evaluation masks them; the execution API selects no sealed column and names its columns (no `SELECT *`, no `to_jsonb(row)` anywhere in the crate); audit events carry ids and states only; there is no SSE route for executions; a Flow trigger's context and `trigger.outputs` carry the mask; neither replay (the retry replay starts with no task runs, the replay route copies inputs only) nor any other writer copies `executions.outputs`; egret has no execution restart that copies runs; no master key fails the output naming the setting. `secret()` in an output's `value:` is refused at save (`secret_outside_plugin_task`, on the flow's and a `Loop`'s outputs) and at run (the confined refusal: outputs render without the plugin secret resolver), so a workspace secret cannot be copied into a STRING output the API returns. **Not masked, as for SECRET inputs (KI-112):** a task's own outputs that render a revealed SECRET output (a `Return` of `{{ outputs.sub.outputs.s }}`): the author chose to publish it.
    - **FILE, the output rule (verified).** A FILE output (flow or `Loop`) is accepted for the execution's own file and for any file of its loop family, a sibling iteration's included; refused for a replay source's file (which `read()` admits through the replay chain), a trigger execution's, an unrelated execution's, a `kestra://` URI that is not an execution file, `nsfile://` and `file://`.
    - **FILE, a parent reads its `Subflow` child's published files (closed by B4).** Kestra lets a parent `read()` its child's file outputs (OSS allows every namespace); egret's readable set did not reach a child, so `{{ read(outputs.sub.outputs.f) }}` failed. `storage::resolve_readable_for_read` is now the decision of every READ (the render snapshot, so every render function and staged URI, and the FILE-input check of an execution-creating INSERT): `resolve_readable_many`, plus a URI that is a string value of a child's flow outputs as copied onto a `Subflow` run of an execution in the reader's readable set, when the child row's `trigger_execution_id`/`trigger_run_ix` name that run and its id is the run's `executionId` (so a script's look-alike map publishes nothing), and the URI's `{exec}` is in the child's own loop family (so a child's STRING output cannot launder a third execution's file). Only the URI is admitted, never the child's other files. Not used by the FILE-output rule: a parent that re-publishes the child's file as its own FILE output is refused (D10; Kestra accepts it, §6 item 2), nor by the files API, whose authority is over the execution its route names. The `NotReadable` message names the new case.
    - **Caps (verified).** 1 MiB per `Loop` iteration's FETCH map, 16 MiB per `Loop` list (`{uri}` entries included), `max_file_bytes` on a STORE file, 16 MiB per execution's flow outputs; the `Subflow` copy and `trigger.outputs` copy a stored map and so inherit its 16 MiB. One derived bound: a `dependsOn` fire deep-merges the event's outputs with the window creator's, so a trigger record's `outputs` is at most 2 × 16 MiB; no refusal added (Kestra has none).
    - **Limit recorded:** the pruner's protected set does not include a child's published files while the parent still runs; a parent that reads one more than the retention period after the child ended gets the `Pruned` refusal, never another file.

### 2.3 Design decisions

Controller decisions under the autonomy rules. Each names the survey section it comes from.

- **D1. Where a `Loop`'s outputs are evaluated (survey §2 items 1–4).** In the settle that ends an iteration's sub-execution, after its `errors:`/`finally:` have run, on the sub-execution's own render surface (its task outputs, `item`, the inherited parent outputs; the surface `claim::settle`'s outbox phase already loads), and only when the `Loop` declares a non-empty `outputs:`. A render or coercion failure appends `FAILED` to the sub-execution's state history **after** the terminal it reached (`CREATED RUNNING SUCCESS FAILED`, as golden `loop-outputs-failed-render`), persists it, logs the error on the sub-execution, and the report to the parent `Loop` is `FAILED`. The computed outputs travel with the terminal report into `spawn::on_execution_terminal` (`EW src/worker/spawn.rs:519-657`), which today receives only the state.
- **D2. One outputs evaluator for both kinds (survey §2 item 3).** A shared function, used by D1 and by D6, ports `renderOutputs` + `typedOutputs`: the **required** outputs (`required` absent or `true`) render together and one failure fails them all; each **optional** output renders alone, and a failure is logged and becomes `null`; then every value is coerced by its `type` with the input coercer of package #3 (`EW src/inputs_check.rs`, Kestra's `parseData`); a coercion error fails. The error text names the output id. The function is pure over a render surface and a list of `FlowOutput`s, and returns the typed map plus the SECRET ids (D9).
- **D3. The `Loop` run's list (survey §2 item 5, §6 D2).** When an iteration ends: if it failed and `transmitFailed` (default `true`) holds, the `Loop` ends `FAILED` at once and that iteration's outputs are **not** appended; otherwise, if its map is non-empty, `{item: {value, iteration, key?}, outputs: {…}}` is appended to the `Loop` run's `outputs` list. `item.value` is the iteration's value as a string, `iteration` the 0-based index, `key` present only for a map value. Order is **termination order** (index order when `concurrencyLimit: 1`). The append happens under the parent row lock `on_execution_terminal` already takes (`claim::load(… Stack::Nested)`), so concurrent iterations never lose an entry.
- **D4. Counters and the cap (survey §2 item 6, Q5).** Every `Loop` run, with or without `outputs:`, carries `iterationCount`, `runningIterations` and `terminatedIterations` (a map from state name to count) in its `task_runs.outputs`, updated under the same lock; `outputs` is present only once an entry was appended, as Kestra. `nextOffset` is not written (egret reads file `values:` by index). **Cap:** an iteration whose FETCH map serialises to more than 1 MiB (`env::MAX_OUTPUT_BYTES`), fails in its own settle: the sub-execution gets `FAILED` as in D1. An iteration whose append would take the list past 16 MiB is decided at the append, under the parent lock (only the parent sees the total): the iteration is treated as a failed iteration (under `transmitFailed` the `Loop` ends `FAILED`; otherwise it is not appended and counts under `FAILED` in `terminatedIterations`), and the message is logged on the `Loop` run; the sub-execution's own history is not rewritten after it ended. The message reads `Loop outputs of iteration <i> are <n> bytes; egret keeps at most 1 MiB per iteration and 16 MiB per Loop in the execution. Use fetchType: STORE to keep them in internal storage.` (the 16 MiB variant names the total). The limits are constants beside `MAX_OUTPUT_BYTES`.
- **D5. `fetchType` (survey §2 item 7).** `FETCH` keeps the map. `STORE` writes the typed map as **one ION file per iteration** with `runners::ionfmt::write_ion_element`, under the **sub-execution's** storage prefix (as Kestra's `runContext.storage().putFile`), indexed like a task's output file so the readability rule (`storage::index::resolve_readable_many`) and the pruner know it, and replaces the map by `{uri: "kestra:///…"}`. `AUTO` (the default) is STORE when `values:` is a **string** that renders to a `kestra://` URI egret's storage reads (Kestra's `guessOutputMode`), FETCH otherwise; the decision is taken once per `Loop` run from the rendered `values:`, not per iteration. The 1 MiB / 16 MiB cap of D4 applies to the list of `{uri}` entries too (it is far away). A SECRET output under STORE: see D9.
- **D6. Flow-level `outputs:` (survey §2 item 8, note 6).** Evaluated with D2 when an execution reaches its terminal state, **before** `afterExecution:` is scheduled (so `{{ execution.outputs.x }}` renders in `afterExecution:`), and only when the flow declares `outputs:`. Stored in the new `workflow.executions.outputs` (D11). A failure appends `FAILED` after the computed terminal (`CREATED RUNNING SUCCESS FAILED`, as golden `flow-with-outputs-failed`) and the error is logged on the execution. Where the value appears:
  - `{{ execution.outputs }}` in every later render of the execution (`afterExecution:`; `worker/render.rs:279-284` reads the column); **built by Task B2, 2026-10-29:** `Surface::load` reads the column and reveals the sealed SECRET values to the execution's own renders (masked in every line they write); `NULL` renders `{}` as before; a Flow trigger's render context over the execution gets the mask (§2.2 item 11); the outputs are capped at 16 MiB (§2.2 item 10);
  - a parent's `{{ outputs.<subflow>.outputs }}` (`worker/subflow.rs:774-779` copies the child's outputs onto the `Subflow` task run when the child ends, `wait: true` only, as Kestra);
  - a Flow trigger's `{{ trigger.outputs }}` (the triggering execution's outputs, as Kestra);
  - the execution API (`GET` of an execution and the list carry `outputs`; OpenAPI updated). *Corrected 2026-10-30 (fix wave 6, I4): the detail only.*
  **Inside a `Loop` iteration the parent flow's `outputs:` are not evaluated:** `sub_flow_source` clears `outputs` on the iteration's flow. Kestra's source evaluates the parent's outputs in every iteration (`onEnd` uses the parent flow); egret treats that as a Kestra bug (roadmap #20 rule, the `WorkingDirectory` `finally:` precedent) and records it (§6). No corpus flow has both, so no bank moves either way.
- **D7. `Loop` retry inheritance (survey §1, Q2).** When `sub_flow_source` builds an iteration's flow, it finds the nearest `retry:` on the `Loop` or on one of its ancestors in the **parent** flow's task tree (Kestra's `searchForParentTaskWithRetry` over `Flow.findParentTasksByTaskId`) and attaches it to the iteration as an **inherited policy**, a new field distinct from the flow-level `retry` so the two keep their meanings. `retry::policy_for` consults it after the run-parent chain and before `plan.retry`: own `retry:` > ancestor inside the iteration > inherited from the parent flow > the flow's own `retry:`, which is Kestra's precedence. It applies to runnable tasks and `Subflow`, as Kestra (`Loop`'s own run never retries). A `CREATE_NEW_EXECUTION` policy reached this way stays refused at run by `worker::replay`, because Kestra throws there too (`OE baseline.txt:352-356`). **The terminal report (survey R3):** a `FAILED` immediately followed by `RETRYING` in the same settle must not report a terminal state to the parent `Loop`; only the state a settle ends in is reported today (`EW src/worker/claim.rs:3509-3516`), and A6 pins it with a test before relying on it.
- **D8. Save-time warnings and property-treatment honesty (survey §1, §3; Q1, Q2).** Because Q1 puts everything in one PR, nothing ships a warning that the same PR removes:
  - the `not_honoured` warning for `Loop` `outputs`/`fetchType` (`keys.rs:167`, its test at `:1769`) is removed;
  - no warning is added for the flow-level `outputs:` or `Loop` `retry:`; both run once this PR lands;
  - a `Loop` declaring `outputs:` gets the save-time check flow outputs already have (each output has a `type`; ids unique; `validate.rs:1088-1096` reused);
  - a SECRET output on a `Loop` whose `fetchType` is `STORE`, or `AUTO` with a string `values:`, is refused at save (D9);
  - `property-treatment.json`: `Loop.outputs` and `Loop.fetchType` go from "ignored" to "honoured"; the schema `README.md` states that "honoured" there means *saved and passed to the run*, that package #1 measured only the save path, and that `Flow.outputs` and `Loop.retry` were recorded "honoured" before anything ran them (fixed by #6). A fence test asserts that every key the treatment file calls "honoured" on the `Loop` row and on `Flow` is either run by egret or listed in `keys.rs`'s `not_honoured` table, with the three keys of this package named in it.
- **D9. SECRET outputs (Q3).** The `secret_inputs` mechanism is reused, not copied:
  - the stored value (the `Loop` run's list, `workflow.executions.outputs`, a `Subflow` run's copy) holds `MASK` (`logs::MASK`) for each SECRET output, and the real values are sealed, one JSON object per row, with `egret_secrets::Crypto` under `secrets.master_key` (`secret_inputs::CIPHER`) into a `bytea` column beside it: `workflow.executions.secret_outputs` and `workflow.task_runs.secret_outputs` (D11). For the `Loop` list, the sealed object is keyed by list position. *Corrected 2026-10-30 (fix wave 6, final review I1): a `Loop` run's column is append-only frames, one sealed `{id: value}` object per entry with a SECRET value, each prefixed by its list position and length (`secret_inputs::seal_loop_entry`), so an iteration end never re-seals the list;*
  - only the worker's render surface (`worker::render::Surface::load`) opens them, so a later `{{ outputs.loop.outputs[0].outputs.s }}` or `{{ execution.outputs.s }}` renders the real value; every log line and failure message of the run masks them (`RenderContext::redactions`);

## 6. Recorded divergences

1. **The parent flow's `outputs:` are not evaluated inside a `Loop` iteration** (D6). Kestra's source does. No corpus entry.
2. **FILE outputs and STORE URIs outside the execution's loop family are refused** (D10, Q4, security). Kestra OSS accepts any URI. This includes a parent re-publishing its `Subflow` child's file as its own FILE output; the parent can still READ it (Task B4, §2.2 item 14), as in Kestra.
3. **`Loop` outputs are capped** at 1 MiB per iteration and 16 MiB per `Loop` (D4, Q5). Kestra has no cap. **Flow-level outputs are capped at 16 MiB per execution** (controller decision 2026-10-29, §2.2 item 10).
4. **A SECRET output under STORE is refused at save** (D9). Kestra writes the encrypted form.
5. **A deployment without a master key fails a SECRET output** (D9), as it refuses a SECRET input start. Kestra fails too (the reason `subflow-secret-output-*` stay baselined). *Corrected 2026-10-29 (Task Z): because both oracle harnesses run without a key, the two entries banked (Q3).*
6. **Concurrent iterations' order** is egret's termination order; Kestra's is non-deterministic as well (survey R5). Not a divergence anyone can measure; recorded so a reader does not pin it.
7. **A `Subflow` child that ended before `RUNNING` and declares only literal outputs fails the `Subflow` run in egret** (Task B3, §2.2 item 13): egret evaluates flow outputs only for an execution that ran and copies what was stored; Kestra re-renders them in the parent and would publish the literals. No corpus entry.
8. **Duplicate output ids on a `Loop` are refused at save** (`duplicate_output_id`, Task A1, §2.2 item 8). egret-only: Kestra refuses duplicates in the flow's `outputs:` (`FlowValidator.java:107-111`), which egret now does too, but never looks inside a `Loop`'s; egret refuses there as well, because a duplicate would silently overwrite the other in the iteration's map. D8's premise that the check already existed was half wrong.
9. **A STORE file is named `outputs.ion`** (`kestra:///{ns}/{flow}/executions/{iteration}/outputs.ion`, Task A5), where Kestra's is a random `{n}.ion`; a settle that runs again overwrites its own object (the SQL STORE `result.ion` precedent). Measured against the artifact's run of `loop-outputs-auto`: the only field that differs besides `nextOffset` (item 10).
10. **`nextOffset` is not written** on a `Loop` run (D4): egret reads file `values:` by index.
11. **The read rule's `Subflow` widening crosses the one trigger hop the read set already crosses** (Task B4, recorded 2026-10-30, final review m3). `resolve_readable_for_read` admits a file a waited-for `Subflow` child published to **any execution of the reader's read set**, which holds the reader's loop family, its replay chain and its trigger execution with that one's loop family. So a Flow-triggered execution (any namespace of the workspace) can `read()` a file its source's `Subflow` child published, and a `Subflow` child can read a file a sibling child published to their common parent. Nothing beyond that hop: the child must be the run's own, and the URI the child's own. Kestra OSS lets every namespace read every file, so this is narrower than Kestra.
12. **A revealed SECRET value that a render copies into a `Subflow`'s inputs or into a STRING flow output is stored in clear** (KI-112 family, recorded 2026-10-30, final review m2): `{{ outputs.loop.outputs[0].outputs.s }}` rendered into a child's `inputs:` is stored in the child's `inputs`, and rendered into a `type: STRING` flow output it is stored in `workflow.executions.outputs`; the API returns both. This is the same class as a task's own outputs (§7 known limits): the render surface reveals the value to the execution's own renders, and what the author writes elsewhere is the author's. Masking by value (refusing a STRING output equal to a redaction) was not done: it would silently change the value of any output that happens to equal a secret.
13. **A `dependsOn` fire whose merged `trigger.outputs` would pass 16 MiB is refused**, and so is an event whose outputs a window would store past 16 MiB (egret-only, fix wave 6, final review I4): the listener does not fire on that event, the window is kept, and the log names both sizes. Kestra has no limit.
14. **An iteration refused by the 16 MiB total under `transmitFailed: false` is counted under `FAILED`** in `terminatedIterations` while its sub-execution's own history stays `SUCCESS` (D4, intended; recorded 2026-10-30, final review m10): the sub-execution's history is not rewritten after it ended, and the refusal is logged on the `Loop` run.

| A `Loop` with `outputs:` | the keys were accepted with a `not_honoured` warning; nothing evaluated them; `{{ outputs.loop.outputs }}` failed to render | the outputs are evaluated at the end of each iteration and appended as `{item: {value, iteration, key?}, outputs}` to the `Loop` run's `outputs` list (termination order; index order with `concurrencyLimit: 1`) |

**egret-only limits (Kestra has none):**
- A `Loop` iteration's outputs (FETCH) may serialise to at most **1 MiB**, and a `Loop`'s whole list to **16 MiB**; beyond either, the iteration fails with a message pointing to `fetchType: STORE`. A flow's outputs may serialise to at most **16 MiB** per execution; beyond it, the execution fails with a message pointing to a FILE output.
- A `type: FILE` output (flow or `Loop`) must name a file of the execution itself or of its `Loop` family (`egret refuses output <id>: <uri> is not a file of this execution`): another execution's file, a trigger's or replay source's file, `nsfile://`, `file://`, a namespace file or a malformed value is refused. A parent cannot re-publish its `Subflow` child's file as its own FILE output.
- A SECRET output under `fetchType: STORE` (or `AUTO` over a file) is refused at save and at run (the file would hold the value in clear). SECRET outputs elsewhere are sealed with `secrets.master_key` and shown as `******` in the API and in logs; a deployment without a master key fails the output naming the setting.
- Duplicate output ids inside a `Loop`'s `outputs:` are refused at save (`duplicate_output_id`); Kestra checks the flow's list only.
- `secret()` in an output's `value:` is refused (save and run).
- A `dependsOn` Flow trigger does not fire on an event whose `trigger.outputs` (the event's flow outputs deep-merged with the window's) would pass **16 MiB**; the log names the sizes and the window is kept.

**Known differences from Kestra:**
- The parent flow's `outputs:` are not evaluated inside each `Loop` iteration (Kestra's source does; treated as a Kestra bug).
- A STORE file is named `outputs.ion` (Kestra: a random `{n}.ion`); `nextOffset` is not written.
- A `Subflow` child that ended before `RUNNING` and declares only literal outputs fails the `Subflow` run (Kestra would publish the literals).
- `{{ trigger.outputs.x }}` works in a Flow trigger's `inputs:`, not yet in the fired flow's tasks (roadmap row #11).
- An iteration's stored flow source carries an egret key `x-egret-inherited-retry` (the inherited policy); a flow written with it is refused at save.
- A `retry:` with `behavior: CREATE_NEW_EXECUTION` that reaches a task inside a `Loop` saves with a `not_honoured` warning and is refused at run, as Kestra throws there too.
- An iteration refused by the 16 MiB total under `transmitFailed: false` is counted under `FAILED` in the `Loop`'s `terminatedIterations`, while the iteration's own execution shows `SUCCESS`: its history is not rewritten after it ended, and the reason is logged on the `Loop` run.
- A SECRET output's real value is revealed to the execution's own renders, so a value an author renders into a `Subflow`'s `inputs:` or into a `type: STRING` flow output is stored there in clear and returned by the API (the KI-112 class: the author chose to publish it). Keep SECRET values in SECRET outputs and inputs.
