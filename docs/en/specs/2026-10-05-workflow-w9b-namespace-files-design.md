# W9b — Namespace files: `nsfile://`, `fileURI`, `namespaceFiles`, the `core.namespace` tasks and the namespace file API

**Status:** design, 2026-10-05; not yet implemented
**Depends on:** W9a (internal storage: `egret-storage` streaming, the process-wide `FileStore`, `storage::uri`, the pre-render file scope, streamed transfer, the plugin storage bridge, the bounded multipart parser, the file API's safe download headers, the pruner) — merged. W5a (script tasks, `inputFiles`), W5b (plugin host, `task.json`) — merged. Base `e539d8b3`.
**Programme spec:** `docs/{en,vi}/specs/2026-09-01-workflow-programme-design.md` §3 finding 4 (`StorageInterface`), §9 (row W9); W9a spec `docs/{en,vi}/specs/2026-10-01-workflow-w9a-internal-storage-design.md` §14 (namespace files deferred to W9b)
**Decided with the user, 2026-10-05:**
- **Namespace files keep revisions, as Kestra does.** Revision 1 lives at `path`, revision N > 1 at `path.vN`; a delete is soft; `PurgeFiles` hard-purges (§3, §4, §8.4).
- **A running flow reads namespace files of any namespace in its workspace, and writes only to its own namespace.** Writes are `UploadFiles`, `DeleteFiles`, `PurgeFiles` (own namespace and its child namespaces) and a plugin's `putFile`. The workspace is the hard boundary, taken from the running execution and never from a URI (§5).
- **API permissions:** reading (download, list, search, stats, revisions, export) needs `workflow:read`; writing (upload, create directory, move, delete, purge) needs `workflow:manage`. No new permission (§9).
- **In scope:** the store and its metadata (`workflow.namespace_files`, objects at `{prefix}{ws}/{ns-as-path}/_files/{path}[.vN]`, `kestra:///{ns-as-path}/_files/…` URIs through a new `Tail::NamespaceFile`, `nsfile://` parsing) (§3, §4), the expression functions (§6), `namespaceFiles` on script tasks, parsed and validated only on `WorkingDirectory` (§7), the four `io.kestra.plugin.core.namespace` tasks as native handlers (§8), the REST API (§9) and the plugin bridge (§10).
- **(Added 2026-10-05, the user's ruling on the spec's `WorkingDirectory` finding.) `WorkingDirectory` stays out of W9b.** W9b runs `namespaceFiles` on script tasks only. On `WorkingDirectory` the block is parsed and validated at publish: a malformed block is refused, naming the property; a valid one is accepted and kept in the model for the later package that runs `WorkingDirectory`. Nothing changes at run, because egret still does not execute `WorkingDirectory` (§1, §7). The two corpus flows stay baselined, and no ratchet change is expected (§13). *(Note 2026-10-05, Task 1 measured; the ruling's text above is unchanged: the two corpus flows are not baselined, they stand **outside the ratchet entirely** — the artifact refused both at publish (422 `Invalid type: io.kestra.core.tasks.test.Read`), so they have no golden entry and no line in `baseline.txt`. The ruling's substance holds: no ratchet change can come from them.)*
- **(Added 2026-10-05, the user's ruling on `inputFiles`.) As in Kestra, namespace files load first and `inputFiles` always overwrite a same-named namespace file, whatever `ifExists` says; `ifExists` governs only collisions between namespaces** (§7). Task 1 still measures it.
- **(Added 2026-10-05, the user's ruling on `_files` namespaces.) A namespace with a `_files` segment is refused** at publish and in every namespace-file operation (API, tasks, functions), with an error naming it. Task 1 counts the existing flows and corpus entries with such a namespace, and its report lists each one (§3).
- **(Added 2026-10-05, the user's ruling on the plan's open item 9.) A script task's `inputFiles` value that is a namespace-file URI (`nsfile:///…`, `nsfile://other.ns/…`, or `kestra:///…/_files/…`, e.g. from `fileURI`) is accepted, as Kestra does:** it is staged into the task's working directory through the same one namespace-file read check (any namespace of the workspace), alongside W9a's execution-file URIs (§7).
- **(Added 2026-10-05, the controller's ruling on the plan's open item 10.) `task.json` carries namespace files in a separate `namespaceFiles` array** (URI, namespace, path, revision, size, staged path); W9a's `storage` map (URI → staged path) is unchanged (§10).
- **(Added 2026-10-05, the user's ruling on the detailed choices.) Approved as egret's choices**, each a row in §2: `PurgeFiles` defaults to the flow's own namespace; child namespaces match on a dot boundary; the API's `DELETE` does not remove parents left empty; export is a streamed, files-only zip; `fileURI` without `revision` is an error on a missing path; reading `kestra:///other/ns/_files/…` is allowed within the workspace.
- **(Added 2026-10-05, the user's ruling R1 in Task 1's fix round 1.) Soft-deleted history stays visible**, unlike Kestra's 404s: the `revisions` API lists every revision of a soft-deleted path, the deleted ones flagged; an explicit-revision read (`GET …/files?path&revision=N`, `read(path, revision)`, `fileURI(path, revision)`) of a revision of a soft-deleted path succeeds; a **latest** read (no revision) of a soft-deleted path is not-found. Rewriting it creates a new revision, as before (§2, §4.3, §4.5, §6, §9). *(Clarified 2026-10-05, fix round 2, the coordinator's ruling A: a `kestra:///…/_files/…[.vN]` URI names exactly one revision — revision 1 without a suffix — so reading it is an explicit-revision read too.)*
- **(Added 2026-10-05, the user's ruling R2.) `PurgeFiles.namespacePattern` uses Kestra's wildcard grammar** (`FilenameUtils.wildcardMatch`: `*`, `?`; `w9b.pp.*` does not match `w9b.ppx.c`), restricted to the flow's own namespace and its children (the purge rule, §5) (§2, §8.4).
- **(Added 2026-10-05, the user's ruling R3.) `fileURI` of a directory is an error naming the path; search is as Kestra's (case-insensitive substring, files only); `GET …/files/directory` on a file's path is 400; GET routes never create anything (stats with no path answers a virtual root directory and creates nothing)** (§2, §6, §9).
- **(Added 2026-10-05, the user's ruling on Task 2's review, finding I1.) The `_files` marker counts only before the first `executions/{uuid}` pair.** After that pair, `_files` is part of an execution file's path, as in W9a: a task output under a `_files/` directory and a FILE input named `_files` stay execution files. A flow id `_files` is refused at publish; Kestra's id pattern already refuses a leading `_`, and a flow's slug holds no `_` (§1, §3).
- **(Added 2026-10-05, the user's ruling on Task 2's review, finding I2.) A namespace file path is at most 512 bytes of UTF-8 in its stored form**, counting the leading `/` and a directory's trailing `/`. A longer path is an author error naming the path and the rule, so a long path never becomes an infrastructure error at write time (§2, §3).
- **(Added 2026-10-05, the user's ruling on Task 3's review, finding I2.) A move onto a target with ANY history is refused**: a live row or soft-deleted revisions at the target, under it (every path a directory move would write), of the other kind at it, or a file where one of its parent directories goes, is a 409-class conflict naming the target; nothing is purged. History stays until `PurgeFiles` (R1), so a move never purges it implicitly (§2, §4.4).
- **Decided with the user (2026-10-05), on Task 3's re-review, finding I-R1: a write never purges history implicitly, in either direction.** A write that puts a file or a directory where an entry of the other kind is soft-deleted but still holds history is refused with a 409-class conflict naming the path: a directory `/f/`, or a file `/f/x`, while the file `/f` is soft-deleted with its revisions; a file `/q` while the directory `/q/` is soft-deleted with files under it that keep history; any parent directory where a soft-deleted file sits. To reuse the path, the author runs `PurgeFiles` first. Rewriting the same kind over a soft-deleted file still creates a new revision (R1). A soft-deleted directory with no history under it holds no object and no revision; its row is removed and the write goes on (§2, §4.2).
- **Decided with the user (2026-10-06), on Task 5's review (I2, M4, M6).** (a) **A namespace file whose name holds glob characters** (`*`, `[`; legal for a path, §3) **stages as in Kestra.** Names staged into a working directory are checked by a name rule without the glob clause; it still refuses an empty name, an absolute path, a `..` segment, a control character and the `.`-directory spellings, and the rule for every other caller (outputs, collection, an `inputFiles` key) is unchanged. (b) **`ifExists`, `include`, `exclude` and `namespaces` accept expressions, as Kestra's `Property` does.** They are rendered at run in the task's render scope and then type-checked: `ifExists` must be one of `OVERWRITE`/`FAIL`/`WARN`/`IGNORE`, and a list expression must render to a list of strings; the error names the field and the value. A literal value is still checked at publish, and `namespaces` still defaults to the flow's own namespace (Kestra's `["{{flow.namespace}}"]`). (c) **When a namespace file collides with the task's own script file** (`main.py` for `python.Script`), **the task's script wins**, and one WARN line in the task's log names the skipped namespace file (§2, §7).
- **Decided with the user (2026-10-06), on Task 7's review (C2, M1/C5).** (a) **`PurgeFiles` with `behavior: {type: version}` and neither `keepAmount` nor `before` is refused**, and the error tells the author to set one of them and that `keepAmount: 0` purges every revision; Kestra purges every revision of every matched path. (b) **`DeleteFiles.deleteParentFolder` follows Kestra:** a parent is empty when no live FILE remains at any depth under it, and it is soft-deleted together with its empty subdirectories; the check and the delete run in one transaction holding the parent's lock, so a file written into it concurrently keeps it (§2, §8.3, §8.4).
- **Decided with the user (2026-10-06), on Task 8's review (I-1): staging. A namespace file's body is uploaded before any lock is taken.** Every write (the API, `UploadFiles`, every other caller of the store's write) first streams the body, under the file cap, to a unique staging object `{prefix}{ws}/_nsfiles_staging/{uuid}` while it holds no database connection and no advisory lock. Only then does one short, server-paced transaction lock the path, apply the kind and conflict rules and the re-claim skip, pick the revision, copy the staging object onto the revision's key server-side, check its size, insert the row and commit; the staging object is deleted afterwards, whatever happened. Staging objects a crash leaves are bounded: each has a row, and an hourly sweep deletes those older than 24 hours (§4.2, §8.1, §11, §15).

**Delivery:** one PR (docs and code), ten tasks in §12, implemented by a plan written after this spec.

## 2. What Kestra does, and where egret differs

Kestra (checkout `96893b589`, artifact `2.0.0-rc13`):
- **Layout.** Namespace files live under `/{ns-as-path}/_files` (`StorageContext.java:41`, `namespaceFilePrefix` `:324-326`). Revision 1 is stored at `path`, revision N > 1 at `path.vN`; a directory is always revision 1 (`NamespaceFile.java:138-148`). The metadata repository gives a write `previous + 1` (a directory stays 1) (`AbstractJdbcNamespaceFileMetadataRepository.java:191-199`), reading `previous` through `findByPath`, which runs its own transaction (`:69-80`). A soft delete marks the latest row deleted without a new revision (`:203-205`).
- **`Namespace`** (`core/…/storages/Namespace.java`): `all`, `children`, `move`, `get`, `findAllFilesMatching(includes, excludes)`, `getFileContent(path, revision?)`, `getFileMetadata`, `exists`, `putFile(…, Conflicts)` with `Conflicts { OVERWRITE, ERROR, SKIP }` (`:186-189`), `createDirectory`, `delete`, `isDirectoryEmpty`.
- **`InternalNamespace`**: writes the object, then creates missing parent directories, then saves metadata (`InternalNamespace.java:338-404`); `ERROR` throws, `SKIP` logs (`:391-399`); a soft-deleted path is rewritten as a new revision (`:372`); a live entry of the other kind (file vs directory) is a `ConflictException`, a deleted one is purged first (`:421-450`); parents are auto-created (`mkDirs`, `:455-466`); `delete` marks the path and all its children deleted (`:495-512`); `move` refuses an existing target, copies every revision, then purges the source, rolling back the copies on failure (`:130-215`) — *(amended 2026-10-05, Task 1 measured on the artifact: a file's three revisions move as 1, 2, 3, but a **directory** move carries each child's latest revision only, renumbered 1; a move onto an existing target answers 500)*; `purge` marks metadata deleted before removing the object (`:218-224`); a read goes through metadata and **falls back to an older revision** when the indexed object is missing (`:257-289`).
- **Paths.** `NamespaceFile.normalize` refuses `..` (`NamespaceFile.java:167-178`). The controller refuses `/_flows` (`NamespaceFileController.java:68-70`, `:379-386`) and any path component over 255 characters (`:52-53`, `:254-258`).
- **Functions.** `nsfile:///path` is the flow's own namespace; `nsfile://other.ns/path` names a namespace in the authority; a `namespace` argument together with an authority is an error (`AbstractFileFunction.java:181-191`); a bare path becomes `nsfile:///path` in the `namespace` argument's namespace or the flow's (`:92-95`). `fileURI(path, revision?)` returns a `kestra://` URI; with `revision` it checks that revision exists and refuses a non-integer (`FileURIFunction.java:54-79`); without one it does not check that the file exists (`:76-78`, by the code). `read` returns a `String`, or `byte[]` for binary Ion (`ReadFileFunction.java:69-76`), and takes `revision` (`:78-89`). OSS `isAllowedNamespace` is always true (`NamespaceService.java:43-45`, called from `DefaultNamespaceService.java:39`); there is no parent-namespace inheritance.
- **Script `namespaceFiles`** (`core/…/models/tasks/NamespaceFiles.java`): `enabled` default true when the block is present (`:24-25`), `include`, `exclude`, `namespaces` default `["{{flow.namespace}}"]` (`:42-44`), `ifExists` default `OVERWRITE` (`:49-50`; `FileExistComportment { OVERWRITE, FAIL, WARN, IGNORE }`), `folderPerNamespace` default false (`:55-56`). The loader (`NamespaceFilesUtils.java:44-98`) lists matches per namespace, then writes them **in parallel** (`:69-85`), so between two namespaces holding the same path the order is not enforced; `WARN` logs and keeps the existing file (`LocalWorkingDir.java:202-212`) — *(amended 2026-10-05, Task 1 measured: over five runs per mode `OVERWRITE` kept the later namespace's file, `WARN` and `IGNORE` the first, `FAIL` failed the task; `WARN`'s line did not reach the task's logs)*. Script tasks and `WorkingDirectory` load namespace files **before** `inputFiles` (`CommandsWrapper.java:155-178`, `WorkingDirectory.java:292-298`), and `inputFiles` are then written with a plain `FileOutputStream`, replacing a namespace file whatever `ifExists` says (`FilesService.java:38-58`).
- **Globs** (`PathMatcherPredicate.java`): `glob:` is the default syntax; a pattern starting with a word character gets `**/` prepended (`:112-114`); `regex:` is supported (`:22-23`, `:132-134`); the predicate is includes AND NOT excludes (`:67-78`).
- **Tasks** (`core/…/plugin/core/namespace/`): `UploadFiles` — `namespace` (`@NotNull`, though `run` falls back to the flow's, `:118-122`, `:162`; *amended 2026-10-05, Task 1 measured: publish refuses a missing `namespace` with 422 `tasks[up].namespace: must not be null`, so the fallback is unreachable*), `files` globs over **its own working directory** (`:192-201`), `filesMap` (name → URI, read only if it exists, `:204-222`), `destination` default `/` (`:147-148`), `conflict` default `OVERWRITE` (`:150-156`), returns an empty `Output` though `Output.files` is declared (`:187`, `:224-228`). `DownloadFiles` — `namespace` required, `files`, `destination` default `""`; output path → `kestra://` URI (`DownloadFiles.java:81-145`). `DeleteFiles` — `namespace`, `files`, `deleteParentFolder` default false; soft (`DeleteFiles.java:80-176`). `PurgeFiles` — `filePattern` (Commons-IO wildcard), `namespaces`, `namespacePattern`, `behavior` default `Version { keepAmount: 1 }`, `includeChildNamespaces` default true; hard purge; output `size` (`PurgeFiles.java:59-130`, `Version.java`, `PurgeTask.java`, `NamespaceFileService.java:95-115`).
- **API** (`NamespaceFileController.java`, `/api/v1/{tenant}/namespaces`): `GET {ns}/files/search?q` (`:73`), `GET {ns}/files?path&revision` (`:82`), `GET {ns}/files/stats` (`:101`), `GET {ns}/files/revisions` (`:126`), `GET`/`POST {ns}/files/directory` (`:154`, `:180`), `POST {ns}/files` multipart, `.zip` expanded (`:196-235`), `_flows/x` imports a flow (`:236-246`), `GET {ns}/files/export` (zip in memory, `:269-308`; the checkout adds the namespace's flows as `_flows/*.yml`, but *(amended 2026-10-05)* the artifact measured by Task 1 exported the files only, with no `_flows` entry, from a namespace holding a flow), `PUT {ns}/files?from&to` (`:312`), `DELETE {ns}/files` (`:332`). No `@Secured` in OSS.
- **Lifecycle.** Soft-deleted entries stay until `PurgeFiles`; `PurgeStorage` handles execution storage only; no cleanup on namespace deletion was found.

## 3. Storage layout and URIs

- **Object key:** `{workflow.storage.prefix}{workspace_id}/{ns-as-path}/_files/{path}` for revision 1, `…/{path}.v{N}` for N > 1; a directory has no object (its row is the directory), unlike Kestra's `createDirectory` on the store. Same bucket and prefix as W9a.
- **URI a flow sees:** `kestra:///{ns-as-path}/_files/{path}[.vN]`, Kestra's form. Like W9a's it carries no workspace: egret maps it to a key by prefixing the running execution's workspace.
- **`Tail::NamespaceFile { path, revision }`** joins W9a's `Tail` in `storage/uri.rs`. `parse` recognises the **first** segment equal to `_files` at index ≥ 1 as the namespace file marker: segments before it are the namespace, after it the path; a trailing `.v{N}` (N ≥ 2, digits only) is the revision. *(Amended 2026-10-05, the user's ruling on Task 2's review, I1.)* The marker counts only when it comes **before the first `executions/{uuid}` pair**. After that pair, `_files` is part of an execution file's path, so W9a's `…/executions/<uuid>/tasks/<slug>/<run>/_files/report.csv` and a FILE input named `_files` stay execution files. So `kestra:///a/_files/x/executions/<uuid>/f` is namespace `a`'s file `/x/executions/<uuid>/f`, never an execution URI of a flow `_files`, which cannot exist (§1). A namespace holding `executions.<uuid>` before `_files` has no URI for its files (W9a's documented non-totality); building one is refused, naming the namespace.
- **A namespace with a segment `_files`** (`a._files`, legal by `is_valid_namespace`) would put its flows' execution keys under namespace `a`'s files. Such a namespace is refused (the user's ruling, header): publish refuses it from W9b on, and every namespace-file operation (API, tasks, functions) refuses it as a target or an authority, each with an error naming the namespace and the segment. *(Added 2026-10-05, Task 2 fix round 1.)* Namespace-file operations also refuse a namespace with an empty segment (`a..b`, `a.`): its key would hold `//`, and no URI could name its files. Publish still accepts such a namespace, unchanged, but a flow whose own namespace has an empty segment cannot use namespace files at all, **Read included**: `authorize` checks the running flow's own namespace with the same rule for every access, so `read('nsfile://shared.cfg/x')` from a flow in `a.` fails naming its namespace and the empty segment (*added 2026-10-05, an application of the M3 rule*). Task 1 counts the published flows in a dev database and the corpus entries whose namespace has one, and its report lists each (none is expected).
- **`nsfile://`** parses as: no authority (`nsfile:///path`) → the running flow's namespace; an authority (`nsfile://other.ns/path`) → that namespace, checked with `nsfiles::access::check_namespace` (`is_valid_namespace`, no empty segment, no `_files` segment). A bare path (no `://`) is `nsfile:///path`.
- **Path rules**, one function for every entry point (functions, tasks, API, plugin bridge): a leading `/` (added when missing); no empty, `.` or `..` segment; each segment ≤ 255 characters; the whole path ≤ 512 bytes of UTF-8 in its stored form, counting the leading `/` and a directory's trailing `/` (*added 2026-10-05, the user's ruling on Task 2's review, I2*); not `/_flows` or under it; W9a's refused characters (`\`, `?`, `#`, control characters); a file's last segment must not end in `.v{digits}` (it would read as a revision of another path). A path that breaks a rule is an author error naming the path and the rule.
- **The prefix budget** *(added 2026-10-05, W9b Task 3, finding R3 of Task 2's review)*: the 512-byte path keeps a namespace file's key under S3's 1024-byte limit only while `workflow.storage.prefix` is short. After the prefix a key holds at most 36 (workspace) + 1 + 150 (namespace) + 1 + 6 (`_files`) + 512 (path) + 12 (`.v` and a revision) = 718 bytes, so `WorkflowStorageConfig::validate` refuses a prefix over **200 bytes** at boot, naming `workflow.storage.prefix`.

## 4. Core

### 4.1 The metadata table

`workflow.namespace_files` (migration 0169): `workspace_id` (FK to the workspace), `namespace` (text), `path` (text, normalised, a directory ending in `/`), `revision` (int ≥ 1; always 1 for a directory), `is_directory`, `size`, `deleted`, `created_at`, `created_by` (the user or the execution that wrote it; *added 2026-10-06, W9b Task 6 fix round 1:* and, for a task's write, the task run, `created_by_task_run`, so a task run re-claimed after an infrastructure failure recognises its own earlier writes, §8.1). Unique `(workspace_id, namespace, path, revision)`; an index on `(workspace_id, namespace, path)` for the latest row. One row per revision; the latest row of a path is its highest revision. No FK to a namespace (there is no namespace table): a namespace with no flows can hold files.

**A namespace file exists only once its row exists**, as W9a's index (W9a §4.2). Reads, `exists`, stats and listings go through the table.

### 4.2 Writing

1. Check the path (§3) and the write rule (§5).
*(Amended 2026-10-06, the user's ruling on Task 8's review I-1: the body is uploaded before any lock is taken. Steps 2 and 3 below are the original design; step 1a and the "Staging" paragraph after the list replace their order.)*

1a. **Stage the body.** Record a staging row (`workflow.namespace_file_staging`: id, workspace, object URI, `created_at`), then stream the body to its staging object `{prefix}{ws}/_nsfiles_staging/{uuid}` under the file cap — holding **no** database connection and **no** lock, so a caller that sends slowly holds nothing another request needs. No other key can be under that segment: every other key of a workspace starts with a namespace's first segment, and a namespace starts with `[a-z0-9]`, never `_` (§3).
2. In one transaction, take a per-`(workspace, namespace, path)` lock (`pg_advisory_xact_lock` on a hash of the three, or `SELECT … FOR UPDATE` on the latest row; the plan picks one and a test runs two writers concurrently), read the latest row, apply the conflict rule (`OVERWRITE` → next revision; `ERROR` → author error naming the path; `SKIP` → no write, reported as skipped), and compute `revision = max + 1` (1 for a new path).
3. ~~Stream the content to the revision's key (`put_stream`), `head` for the size, insert the row, create missing parent directory rows, commit. The lock is held across the upload so that no second writer can compute the same revision;~~ *(amended 2026-10-06, I-1)* **copy the staging object onto the revision's key server-side** (`ObjectStore::copy`, S3 CopyObject), `head` it (its size must be the staged size), insert the row, create missing parent directory rows, commit. The lock is held from the revision's choice to the commit, so that no second writer can compute the same revision, and that window is server-paced. A failed copy rolls the transaction back and leaves at most an unindexed object, which a re-write of that revision overwrites.
4. **File/directory clash:** a live row of the other kind at the path is a conflict error naming it; ~~a soft-deleted one of the other kind is purged first (Kestra's rule)~~. *(Amended 2026-10-05, decided with the user on Task 3's re-review I-R1: a write never purges history implicitly.)* A soft-deleted entry of the other kind that still holds history — a file (it always has revisions), or a directory with files under it that keep theirs — is a conflict error naming it, and so is a file, live or soft-deleted, where one of the path's parent directories goes; nothing is purged, and `PurgeFiles` frees the path. A soft-deleted directory with nothing under it has no object and no revision: its row is removed and the write goes on.
5. **Rewriting a soft-deleted path** creates a new revision (`max + 1`, live); earlier revisions are kept.

**Staging** *(2026-10-06, I-1)*. After step 1a, steps 2–4 run as one short transaction: lock the chain → a `UploadFiles` task run whose own earlier attempt wrote the path's live latest revision skips it (§8.1, judged here under the lock) → the kind rule (step 4) → the conflict rule → revision → copy → `head` → rows → commit. Then the staging object and its row are deleted, on every way out (written, skipped, refused, failed). A process that dies in between leaves the row; an hourly sweep deletes every staging object whose row is older than 24 hours, then the row, and deletes only a key that is exactly that row's staging key (§11).

Caps: `workflow.storage.max_file_bytes` per file, as W9a. *(2026-10-06, I-1.)* One server-side copy moves at most 5 GiB (S3's CopyObject limit); when `max_file_bytes` is configured above that, a namespace file is refused at 5 GiB, naming that limit, rather than copied in parts (§15).

### 4.3 Soft delete

`delete(path)` marks the latest row of the path and of every child deleted, in one statement; objects are kept. Deleting a directory deletes its children. A soft-deleted path is invisible to reads, listings, `exists` and globs, and visible to `revisions` and to `PurgeFiles`. *(Amended 2026-10-05, the user's ruling R1: "reads" here are **latest** reads; an explicit-revision read of a soft-deleted path — `?revision=N`, `read(path, revision)`, `fileURI(path, revision)`, or a `kestra:///…/_files/…` URI, which names one revision — succeeds, and `revisions` lists every revision with the deleted ones flagged.)*

### 4.4 Move

`move(from, to)` refuses an existing live target *(amended 2026-10-05, the user's ruling on Task 3's review I2: and a target with any soft-deleted history — at `to`, under it, of the other kind at it, or a file where one of its parents goes — with a conflict naming it; nothing is purged)*; copies every revision of `from` (and of every child) to `to` keeping revision numbers, inserting rows as it goes; then purges the source (rows first, then objects). A failure during the copy purges every copy already made, in reverse order, and reports the failure naming both paths; nothing of the source is touched before every copy has succeeded.

*(Added 2026-10-05, Task 3 fix round 1.)* `to`'s missing parent directories are created only after every copy succeeded, so a failed move leaves nothing behind. **A move runs to completion once it has started:** it runs on a detached task, so a caller that goes away (a client that disconnects, a task timeout) does not stop it between copies; the answer alone is lost. A hard purge runs the same way. A soft delete and a purge lock the path's whole chain (its parents and itself), as a writer does, so neither runs while a move of an ancestor is copying.

### 4.5 Reading

A read resolves `(namespace, path, revision?)` to a row (the latest live one, or the given revision, which must exist and whose path must not be soft-deleted at its latest revision for a latest-read), then streams that revision's key. **A missing object behind a row is an author error naming the path and revision**; egret does not fall back to an older revision (§2). An unreachable store is an infrastructure error (§11). *(Amended 2026-10-05, the user's ruling R1: a given revision is served even when the path is soft-deleted; only a latest read of a soft-deleted path is not-found.)*

### 4.6 One readability and writability function

`storage::nsfiles::authorize(workspace, running_flow_namespace, target_namespace, Access::{Read, Write, Purge})` decides every access, for the functions, staging, the four tasks, the plugin bridge and (with the user's permission instead of a flow) the API. No caller re-implements the rule. Each refusal has a test that fails when the refusal is removed.

## 5. Who may read and write

- **Workspace:** always the running execution's (or, for the API, the route's `{ws}` after the user's permission check). Nothing in a URI or a property names a workspace.
- **Read:** any namespace of that workspace (`nsfile://other.ns/…`, `kestra:///other/ns/_files/…`, `namespaceFiles.namespaces`, `DownloadFiles.namespace`).
- **Write** (`UploadFiles`, `DeleteFiles`, a plugin's `putFile`/`delete`/`move` — refused anyway, §10): the running flow's own namespace only, compared exactly.
- **Purge** (`PurgeFiles`): the flow's own namespace and its child namespaces (`ns == own` or `ns` starts with `own + "."`).
- A refusal is an author error naming the namespace and the rule; it never says whether a file exists there.

- **Properties as Kestra's:** `enabled` (default true when the block is present), `include`, `exclude`, `namespaces` (default the flow's namespace), `ifExists` (`OVERWRITE`/`FAIL`/`WARN`/`IGNORE`, default `OVERWRITE`), `folderPerNamespace` (default false). *(Decided with the user 2026-10-06, Task 5's review M4.)* `ifExists`, `include`, `exclude` and `namespaces` accept an expression, as Kestra's `Property` does. - **Globs** follow `PathMatcherPredicate`: `glob:` default, `**/` prepended to a pattern that starts with a word character, `regex:` supported, includes AND NOT excludes. ## 8. The `io.kestra.plugin.core.namespace` tasks

Native handlers in the worker, like W9a's `core.storage` tasks. Each follows its Kestra class's properties and outputs (Task 1 extracts and measures them).

### 8.1 `UploadFiles`

- `namespace`: optional, default the flow's; anything else is refused (§5). *(The coordinator's ruling D, 2026-10-05: the spec governs; Kestra requires it at publish.)*
- `files`: a list whose items are whole `kestra://` URIs or globs over the **execution's readable files** (W9a §4.4's readable set, matched on the URI's file path); Kestra globs its own working directory (§2). *(Added 2026-10-06, W9b Task 6 fix round 1, M2: an item that is a namespace-file reference — `nsfile:///…`, `nsfile://other.ns/…` or `kestra:///…/_files/…` — is read through the read rule (§5) as `namespaceFiles` staging reads it (§7) and copied into the flow's own namespace at its namespace path under `destination`; one that names nothing fails the task naming it, never matching nothing silently. In `filesMap` such a value is copied to its key, as Kestra's `filesMap` copies any `kestra://` file.)*
- `filesMap`: name → `kestra://` URI (read-checked) or literal contents. *(Amended 2026-10-05, Task 1 fix round 1: every URI of `files` and `filesMap` is resolved before the first write; one that does not resolve fails the task naming it, and nothing is written. Kestra skips it silently.)*
- `destination` default `/`; `conflict` default `OVERWRITE` (`ERROR`, `SKIP`). *(Amended 2026-10-05, Task 1 fix round 1: `destination` is a directory; a missing leading `/` is added and each file's name is joined to it with exactly one `/` — `destination: up2` and key `m.txt` write `/up2/m.txt`, where Kestra wrote `/up2m.txt`.)*
- Each file is written by §4.2. Output: empty, as Kestra's run returns.
- *(Added 2026-10-06, W9b Task 6 fix round 1.)* **One source per destination path:** two different sources resolving to one path refuse the task before anything is written, naming the path and both sources; the same source named twice is written once (§2; I2). **Bounds:** at most `max_namespace_files` resolved sources and `max_task_bytes` bytes together, each refused before the first write naming the cap (M3). **Per file, not atomic across files:** each file commits on its own, so an author error on a later entry (a conflict under `ERROR`, a file/directory clash, an object gone behind its row) leaves the earlier files written, as Kestra's per-file `putFile` does. **A re-claim is idempotent:** after an infrastructure failure (§11) the same task run is re-claimed and skips every file whose latest revision that task run wrote (`created_by_task_run`), under every conflict mode — no second `OVERWRITE` revision, no `ERROR` against its own write. Another task of the same execution writing the same path is not "itself" (`tasks.UploadFiles.runs.up_conflict_error` still fails) (I1). *(2026-10-06, re-review 1, M-R1.)* Each destination path has exactly one source, so "the latest revision was written by this task run" is enough to prove the file done, and the size is not compared: a re-claim keeps the first attempt's bytes for every file that attempt already wrote, even when the source renders differently on the re-claim (a `{{ now() }}`-style value), under `ERROR` too. *(2026-10-06, Task 8 fix round 1, the user's ruling I-1.)* The skip is also judged inside the write's transaction, under the path's lock (§4.2, Staging): an earlier attempt that commits the path after the task's own pre-check is still recognised, and the write answers "already written" instead of adding a revision or a conflict. Each file's body is staged before the lock (§4.2).

### 8.2 `DownloadFiles`

`namespace` required (read rule), `files` globs, `destination` default `""`. Each match is copied (streamed) to an execution file under the task run's prefix (`tasks/{taskId}/{taskRunId}/{destination}{path}`), indexed at commit as W9a's task files. *(Amended 2026-10-06, W9b Task 6 fix round 1, I4: `destination` is a directory and the path loses its leading `/`; the two are joined with exactly one `/`, so `dl`, `dl/` and `/dl/` give `…/{taskRunId}/dl/up/m.txt` and `""` gives `…/{taskRunId}/up/m.txt`. Kestra concatenates, `dl` → `dlup/m.txt` (§2).)* Output `files`: path → `kestra://` URI.

### 8.3 `DeleteFiles`

`namespace` (optional, default the flow's own; any other refused, §5 — the coordinator's ruling D, 2026-10-05: Kestra requires it at publish), `files` globs, `deleteParentFolder` default false (deletes a parent directory left empty, deepest first). Soft (§4.3).

*(Added 2026-10-06, W9b Task 7 fix round 1; the user's ruling M1/C5.)* A parent directory is **left empty** when no live file remains at any depth under it (Kestra's `isDirectoryEmpty`); it is then soft-deleted with every row under it, its live empty subdirectories included. Parents are judged deepest first, each in one transaction that holds its lock, so a file written into it concurrently keeps it. `DeleteFiles` lists at most `max_namespace_files` live entries (more fails the task naming the cap, before anything is deleted), and it needs `[storage]` like the other three tasks, though a soft delete touches no object (C7). Output `{}`.

### 8.4 `PurgeFiles`

- `namespaces` / `namespacePattern` (exclusive, as Kestra), default the flow's own; `includeChildNamespaces` default true (dot-boundary match); every resolved namespace must pass the purge rule (§5), and a pattern is matched only against the namespaces that hold files in the workspace. *(Amended 2026-10-05, the user's ruling R2: `namespacePattern` uses Kestra's wildcard grammar, `FilenameUtils.wildcardMatch` — `*` any run of characters, dots included, `?` one character, case-sensitive; `w9b.pp.*` does not match `w9b.ppx.c` — and its candidates are restricted to the namespaces holding files that are the flow's own or its children, so a pattern never reaches another namespace and nothing is refused for one it could not match. A listed `namespaces` entry outside the purge rule is still refused by name.)*
- `filePattern`: Commons-IO wildcard (`*`, `?`) on the path, as Kestra's `filterItems`. *(Amended 2026-10-05, Task 1 measured: the string matched is the path **without** its leading `/` — `filePattern: "/q.txt"` purged nothing, `"q.txt"` purged two revisions — so egret matches the pattern against the path with the leading `/` removed.)*
- `behavior`: `Version { keepAmount, before }`, default `keepAmount: 1`. `keepAmount` keeps the N highest revisions of each path; `before` purges revisions updated at or before the instant (`<=`, as amended in §8.4 below) and never the latest; a soft-deleted path is purged entirely (§2).
- **Hard delete:** metadata rows first, then objects (W9a's safe order: a crash leaves an orphan object, never a row pointing at nothing). Output `size`: the number of revisions purged.
- *(Added 2026-10-06, W9b Task 7 fix round 1.)*
  - **`behavior`:** `before` purges revisions created **at or before** the instant (`<=`, Kestra's `LESS_THAN_OR_EQUAL_TO`; C3), never a path's latest. `keepAmount` counts every revision, soft-deleted ones included (Kestra's skip over every version; M6). A `behavior` with neither property is refused (§2, C2).
  - **Paged, per path, by row id (I1, I3).** A namespace's file rows are read in keyset pages of `max_namespace_files + 1` rows by `(path, revision)`; each page's complete paths are judged and purged at once, each by its rows' ids under the path's lock, so a purge planned from an earlier listing never removes a newer file that reused a revision number. Only one file holding more revisions than the cap that `filePattern` takes fails the task, naming it; one `filePattern` does not take is skipped. `filePattern` is applied before anything counts toward a bound.
  - **Per path, not across paths.** Each path is purged atomically (rows, commit, objects). An author error or an infrastructure failure part-way leaves the paths before it purged; a re-claim recomputes from the rows as they then are, so its `size` counts what it purged itself. Once started, the purge runs on a detached task to completion.
  - **Directories (I2, M7).** After a namespace's files, its directory rows are visited deepest first: a soft-deleted one -- and with `keepAmount: 0` a live one -- that `filePattern` takes (matched on `dir/`, without the leading `/`) is removed when no row at all is left under it, decided under its lock, as `put` removes a lone soft-deleted directory (§4.2). Each counts in `size`.
  - **Namespaces (M5).** At most 64 (`MAX_NAMESPACES`) listed and at most 64 covered. The candidates are the namespaces holding files under the flow's own (for a pattern or the default) or under each listed one (with `includeChildNamespaces`); over the bound, the error advises listing them with `includeChildNamespaces: false`. A listed namespace outside the purge rule is refused by name before anything is listed or purged.

## 9. The namespace file API

Under `/api/ws/{ws}/workflows/namespaces/{ns}/files`, mirroring `NamespaceFileController`:

| route | permission | answer |
|---|---|---|
| `GET …/files?path&revision` | `workflow:read` | the bytes, streamed, with W9a's download headers (`application/octet-stream`, sanitised `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, `storage/routes.rs:262`); a given `revision` of a soft-deleted path is served, a latest read of one is 404 (R1, 2026-10-05); a directory's path is 400 (application of R3 (2026-10-05)) |
| `GET …/files/stats?path` | `workflow:read` | size, type, revision, created; no `path` answers a virtual root directory and creates nothing (R3, 2026-10-05) |
| `GET …/files/revisions?path` | `workflow:read` | every revision, deleted ones flagged, a soft-deleted path's included (R1, 2026-10-05); a directory's path is 400 (application of R3 (2026-10-05)) |
| `GET …/files/search?q` | `workflow:read` | live paths containing `q`, capped by count; as Kestra's: a case-insensitive substring of the path, files only (R3, 2026-10-05) |
| `GET …/files/directory?path` | `workflow:read` | live children of the directory; a file's path is 400 naming it (R3, 2026-10-05) |
| `GET …/files/export` | `workflow:read` | a streamed zip of the latest live files (no flows) |
| `POST …/files?path` (multipart) | `workflow:manage` | §4.2 with `OVERWRITE`; reuses W9a's bounded multipart parser; a `.zip` is stored as a file, not expanded |
| `POST …/files/directory?path` | `workflow:manage` | creates the directory and its parents |
| `PUT …/files?from&to` | `workflow:manage` | §4.4; a missing source is 404 (application of R3 (2026-10-05)) |
| `DELETE …/files?path` | `workflow:manage` | §4.3, the named path and its children only; a missing path is 200 and does nothing, as Kestra's (idempotent, application of R3 (2026-10-05)) |

- `{ns}` is checked with `is_valid_namespace` and the `_files` segment rule (§3); a namespace with no flows can still hold files. Unknown path → 404; another workspace's namespace is unreachable by construction (`{ws}` scopes every query).
- `/_flows` is refused (400) on every route; egret imports no flow from here (§2).
- **Errors → status** (the one mapping for every route; application of R3 (2026-10-05)):

| error | status |
|---|---|
| a path rule, a refused namespace (`_files` segment, invalid), `/_flows`, a wrong-kind request (a download of a directory, `directory` on a file, `revisions` on a directory) | 400 |
| no live row (unknown path, another workspace's namespace, a latest read of a soft-deleted path, a move's missing source) | 404 |
| a conflict: a file over a directory, a directory over a file, a move onto a live target, `conflict: ERROR` *(amended 2026-10-05: also a file or directory written over a soft-deleted entry of the other kind that holds history, or under a soft-deleted file, §4.2; a move onto a target with any history, §4.4)* | 409 |
| a cap crossed (`max_file_bytes`, `max_namespace_files`, the multipart body limit) | 413 |
| the store or the database unreachable | 503 |

No message names a storage key or another workspace. A `DELETE` of a missing path is not an error (200).
- **No GET route creates anything** (the user's ruling R3, 2026-10-05), where Kestra's `stats` creates the namespace's root (§2).
- *(2026-10-06, Task 8 fix round 1, M-2.)* **A soft-deleted directory is nothing there on every read route** (404 on the download, `revisions`, `stats` and `directory`); only a LIVE directory is the wrong kind (400). A directory has no revisions, so R1 does not keep it visible.
- *(2026-10-06, Task 8 fix round 1.)* An upload's body is staged before any lock (§4.2); a body that stops arriving for 30 seconds is refused with 408 and writes nothing. *(Added 2026-10-06, Task 8 re-review m-2: so is a body that takes longer than 12 hours in all, however steadily it arrives.)* A write's 200 has no content and no content type. A missing or malformed query parameter is a 400 with the documented error body.
- *(2026-10-06, W9b Task 9.)* **The export.** `200 application/zip`, `Content-Disposition: attachment; filename="{ns}_files.zip"`, `nosniff`; one entry per latest live FILE, named by its path without the leading `/` (no directory entry, no soft-deleted file, no flow). ~~Stored entries with data descriptors,~~ *(superseded below, fix round 1)* UTF-8 names, ZIP64 only where a field overflows. The rows are listed first and the connection returned before the body streams. **Bounds, both refused with 413 before any byte:** the listing's entry count (`max_namespace_files`, which counts directories as well as files, one `list_live`), and **the total bytes one export may read: the sum of the listed rows' sizes may not pass `workflow.storage.max_task_bytes` (5 GiB by default), the controller's choice** (no new setting). As it streams, each object is held to its row's size (read at most one byte past it); a short or long object, a missing object or a store failure after the status line ends the body with an error, so the client sees a broken download *(corrected in fix round 1: on HTTP/1.1 without a length a proxy speaking HTTP/1.0 could pass the truncation as a clean end; the body is now shorter than its `Content-Length`, below)*. A client that goes away stops the export.
- *(2026-10-06, the user's ruling, W9b Task 9 fix round 1, I-2.)* **Each file is read twice.** The first read computes its CRC-32 and holds its length to the row's size; the local header then carries the real CRC and sizes (flag bit 3 clear, **no data descriptor**; ZIP64 where a size or offset overflows, the local header then carrying the ZIP64 extra field with both real sizes), and the second read streams the bytes, which must match the first read's size and CRC: a mismatch (the object changed underneath; objects are immutable per revision key, so it should never happen) fails the export. **Why:** Java's `java.util.zip.ZipInputStream`, the class Kestra's `NamespaceFileController` expands an uploaded `.zip` with, refuses a STORED entry with a data descriptor; this form it reads, so an egret export can be imported into Kestra. The cost is two store reads per file.
- *(2026-10-06, W9b Task 9 fix round 1.)* **`Content-Length`** (I-1) is the archive's exact length, computed before the status line from the names and sizes (ZIP64 records included). A failure after the status line ends the body with an error **short of that length**, so a truncated download is detectable on every HTTP version and at every proxy hop. **A path whose first segment looks like a Windows drive** (`C:`, `c:x`) cannot be an entry name; the export is refused with 400 naming it, before any byte (M-5). **The response body is bounded at 12 hours in all** (`EXPORT_TOTAL_TIMEOUT`, the upload's bound): past it the body ends with an error, short of its length (M-7). The listing cap's 413 says "entries (files and directories)" (M-6).
- utoipa-documented; the frontend client is regenerated with `npm run gen:api`. The UI is W7's.

## 10. The plugin bridge

- `runContext.storage().namespace(ns)` stops throwing W9b: `NO_NAMESPACE_FILES` (`ShimRunContext.java:274-280`) is replaced by a factory over staged namespace files.

## 11. Lifecycle and errors

- **No retention for namespace files:** they are authored content, as in Kestra. Soft-deleted revisions and their objects stay until `PurgeFiles` (or an API delete followed by a purge).
- **W9a's pruner never touches `_files`:** it deletes under execution prefixes only; a test writes namespace files, runs a prune pass, and asserts every object and row survives.
- **No per-namespace deletion** (no namespace table, §15).
- **Errors**, as W9a's: a path-rule violation, a refused namespace, a missing object behind a row, a conflict are author errors naming the path; an unreachable store or database is an infrastructure error (the worker returns `Err`, the run is re-claimed, no attempt spent); a crossed cap fails the task naming the cap. No error names a secret. *(Added 2026-10-06, W9b Task 6 fix round 1, I1.)* A task that writes several namespace files (`UploadFiles`) commits each on its own: an infrastructure failure part-way leaves the earlier files written, and the re-claimed task run skips those its earlier attempt wrote, so the retry neither fails as the author's (a conflict with its own write) nor adds revisions (§8.1). An author error part-way leaves the earlier files written too. ~~*(Known limit, 2026-10-06, re-review 1, M-R2.)* The re-claim check reads the latest revision before `put` takes its lock, so a worker whose lease lapsed while it was still running and that overlaps its own re-claim can produce two `OVERWRITE` revisions or an `ERROR` conflict with its own write.~~ *(Resolved 2026-10-06, Task 8 fix round 1: the check is repeated inside `put`'s transaction, under the path's lock, §4.2, §8.1.)*
- *(Added 2026-10-06, the user's ruling on Task 8's review I-1.)* **Staging objects.** Every write's body is first uploaded to a staging object with a row in `workflow.namespace_file_staging` (§4.2). The write deletes both on every way out; a crash or a dropped request between the upload and the commit leaves them *(amended 2026-10-06, Task 8 re-review m-1: "a crash" alone was wrong, a client that goes away drops the request's future too. Once the body is staged, the commit and the deletion run on a detached task the request awaits, as a move does, so a request dropped from then on still commits and deletes both; only a crash, or a request dropped while its body is still arriving, leaves a row, and at most an object its last single-request upload landed)*, and an hourly sweep, started by every egret process that has a store (any replica's sweep suffices; two sweeps of one row are no-ops), deletes each staging object whose row is older than 24 hours, then the row. Age is the database's clock, never the store's. A staging delete that fails is logged and its row kept, so the next pass retries. A body that stops arriving for 30 seconds on the API is refused (408) and holds no connection or lock meanwhile. *(Added 2026-10-06, Task 8 re-review m-2.)* An API body that takes longer than 12 hours in all is refused (408) too, so no live upload's staging row reaches the sweep's 24 hours: every other write's body is internal storage, read at the server's pace, and the commit after it is one short transaction.
- *(Added 2026-10-06, W9b Task 7 fix round 1.)* `PurgeFiles` is atomic per path, not across paths: an author error (one file past the cap) or an infrastructure failure part-way leaves the paths before it purged, and the re-claim recomputes from the current rows (§8.4).

## 15. Known limits

- A flow writes only to its own namespace; a Kestra flow that uploads to, deletes from or purges another namespace fails on egret, naming the namespace (§5).
- `PurgeFiles` with no `namespaces` purges the flow's own namespace (and children), not every namespace (§8.4).
- `WorkingDirectory`'s `namespaceFiles` is validated at publish and kept, but not run, because egret does not run `WorkingDirectory`; running it is a later package (§7).
- `ifExists` does not protect a namespace file from an `inputFiles` entry of the same name, as in Kestra (§7).
- A plugin reads only namespace files named by a whole property value; one that computes a namespace path at run, or writes a namespace file, fails with a reason (§10).
- A missing object behind a metadata row is an error, where Kestra serves an older revision (§4.5).
- `read` of a binary file is an error, where Kestra returns bytes (§6).
- `UploadFiles.files` globs the execution's files, not a working directory (§8.1).
- No retention: namespace files and soft-deleted revisions keep storage until purged (§11).
