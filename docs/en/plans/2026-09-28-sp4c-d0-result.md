# D0 result — whether a Ranger policy item naming a ROLE matches anybody

**Measured:** 2026-09-28, on branch `feat/sp4c-classification-clearance`.
**Method:** upstream source read (Apache Ranger `3.0.0-SNAPSHOT` at
`0274a6a0bc96`, Trino's built-in `plugin/trino-ranger`), corroborated by a
passive `kubectl logs` read of the one running Trino coordinator on
`kind-egret`. No query was run, and nothing on the cluster was modified.
**Why this exists:** SP4a's D7 measured that a Ranger policy item naming a
**group** matches nobody, by mechanism rather than by a failed query, and that
measurement is why the workspace-assignment grant compiles to an enumerated
member list. Nobody had asked the same question about **roles**. D0 asks it,
because if a role name is equally unresolvable then compiling a classification's
clearance into a role-named `denyExceptions` is a control that does not do what
it says.

**Answer: a Ranger policy item naming a role matches nobody on any engine egret
provisions today, and the failure mode of a role-named `denyExceptions` is to
deny EVERYBODY — the cleared users included.**

---

## 1. Nothing in egret creates, pushes, or serves a Ranger role

egret is the Ranger Admin, so "pushing roles to Ranger" is not the question —
the question is whether a role can travel in what egret *serves*. It cannot,
for three separate reasons.

1. **The plugin fetches roles from a dedicated endpoint egret does not have.**
   Ranger's client asks for roles at `/service/roles/download/<service>`
   (`agents-common/.../plugin/util/RangerRESTUtils.java:47`,
   `REST_URL_SERVICE_GET_USER_GROUP_ROLES`), with `lastKnownRoleVersion` and
   `lastActivationTime` query parameters of its own
   (`RangerAdminRESTClient.getRolesIfUpdated`, line 207). egret's entire
   `/service` surface is the six GET routes in
   `crates/egret-policy/src/ranger/routes.rs:15-31` plus
   `api/crud.rs:18-24` — `plugins/policies/download/{service}`,
   `tags/download/{service}`, `plugins/definitions`,
   `plugins/definitions/name/{name}`, `plugins/services`,
   `plugins/policies/{id}`. **There is no roles route at all**, so the poll
   404s.

2. **A role definition cannot ride along in the policy payload.** The
   `ServicePolicies` envelope egret serves
   (`crates/egret-policy-api/src/dto.rs:21-42`) carries `serviceName`,
   `serviceId`, `policyVersion`, `policyUpdateTime`, `serviceDef`, `policies`,
   `auditMode` and `tagPolicies` — and nothing else. Ranger's own
   `ServicePolicies` has no roles member either; roles are a separate
   `RangerRoles` document with its own version counter, fetched by
   `RangerRolesProvider` (`agents-common/.../plugin/util/RangerRolesProvider.java`)
   on its own schedule. The policy download is structurally the wrong channel.

3. **No writer exists anywhere in egret.** `grep -rni
   "RangerRole|roles/download|createRole|/service/roles"` across `crates/` and
   `deploy/` finds only egret's *own* RBAC role CRUD
   (`egret-controlplane/src/access/mod.rs`, `egret-catalog-engine/src/warehouse_admin`),
   which writes egret's Postgres, never a Ranger role document. This is the
   same shape as D7's third finding: egret serves policies and tags, and pushes
   no principal-membership data of any kind.

## 2. The plugin has no other source of role membership

The Trino coordinator egret provisions runs the official `trinodb/trino:<tag>`
image (`crates/egret-provisioner/src/trino.rs:689`, default `470`) with
`access-control.name=ranger` (`trino.rs:352`), which is Trino's **built-in**
`io.trino.plugin.ranger` access control, not Apache Ranger's `plugin-trino`. In
that plugin, role membership has exactly one source and it is the download
above.

- **The plugin supplies no roles from Trino.** `RangerTrinoAccessRequest`
  (`trino/plugin/trino-ranger/src/main/java/io/trino/plugin/ranger/RangerTrinoAccessRequest.java`)
  calls `super(resource, accessType, user, userGroups, null)` — the fifth
  argument is `userRoles`, and it is hardcoded `null`. Trino's SQL role
  surface is not wired in either: `checkCanCreateRole`, `checkCanGrantRoles`,
  `checkCanShowCurrentRoles` and the rest are all empty no-op bodies
  (`RangerSystemAccessControl.java:684-702`).
- **`null` becomes an empty set, never a wildcard.**
  `RangerAccessRequestImpl.setUserRoles` (line 290) stores
  `userRoles == null ? new HashSet<>() : userRoles`.
- **The only filler is the downloaded role document.**
  `RangerDefaultRequestProcessor.preProcess` (line 131-138) fills an empty
  `userRoles` from `authContext.getRolesForUserAndGroups(user, groups)`, which
  reads `RangerRolesUtil`'s `userRoleMapping` / `groupRoleMapping`
  (`RangerAuthContext.java:104-129`). `RangerRolesUtil`'s constructor builds
  those maps only `if (roles != null)`
  (`RangerRolesUtil.java:44-75`); given `null` it leaves every map empty. And
  because there is no group provider (D7), the `groupRoleMapping` half is dead
  regardless — a role whose members are groups would resolve to nobody even if
  the role document did arrive.
- **The secondary resolution path is off by default.**
  `RangerDefaultPolicyEvaluator.getPolicyItemWithRolesResolved` (line 1025)
  can rewrite a role into users/groups, but only from the same empty
  `getRoleToUserMapping()`, and only when `disableRoleResolution` is false —
  which defaults to `true` (`RangerPolicyEngineOptions.java:44` and `:102`,
  property `ranger.plugin.<svc>.policyengine.option.disable.role.resolution`).
  egret's generated `ranger-trino-security.xml` (`trino.rs:357-367`) does not
  set it.

**Live corroboration (passive; no query, no change).** `kubectl logs` on the
only running Trino coordinator on `kind-egret`
(`demo-trino-coordinator-c54f46974-xwgbt`, which was *not* queried or modified)
shows both halves of this:

```text
org.apache.ranger.authorization.hadoop.config.RangerPluginConfig
  PolicyEngineOptions: { ... disableRoleResolution: true ... }

org.apache.ranger.admin.client.RangerAdminRESTClient
  Error getting Roles; service not found. secureMode=false, response=404,
  serviceName=demo-trino, lastKnownRoleVersion=-1, ...
```

The second line repeats every 30s for the life of the pod, and
`lastKnownRoleVersion` never leaves `-1`: the plugin has never held a role
document. This is a log of the plugin's own state, not an inference from a
denied query — the distinction D7 insisted on.

## 3. The failure mode is deny EVERYBODY, not deny nobody

This is the answer that matters, and it is fail-closed in the data sense and
fail-open in the availability sense: **nothing leaks, and the cleared users are
locked out with everyone else.**

Ranger has no "principal not in set" primitive. A policy item is a *match* only
when its principal set **intersects** the request's:

```java
// RangerDefaultPolicyItemEvaluator.java:131-132
if (!ret && CollectionUtils.isNotEmpty(roles) && CollectionUtils.isNotEmpty(policyItem.getRoles())) {
    ret = !Collections.disjoint(policyItem.getRoles(), roles);
}
```

With `roles` empty, the guard short-circuits and a role-only item **never
matches**. An unmatched item is not a neutral item — what it means depends
entirely on which bucket it sits in:

| bucket | role unresolvable ⇒ | net effect |
|---|---|---|
| `policyItems` (allow) | item never matches | grants nobody |
| `denyPolicyItems` | item never matches | denies nobody |
| `denyExceptions` | item never matches | **the deny stands for everyone** |

The third row is the one SP4c's D1 was about to rely on, and it is decided by
`RangerDefaultPolicyEvaluator.getMatchingPolicyItem`
(lines 1331-1361): the matched deny is discarded **only if** some exception
evaluator returns `isMatch(request) == true`.

```java
if (ret != null && CollectionUtils.isNotEmpty(exceptionEvaluators)) {
    for (T exceptionEvaluator : exceptionEvaluators) {
        if (exceptionEvaluator.isMatch(request)) { ret = null; break; }
    }
}
```

So a clearance compiled as *deny `{public}` / except role `analyst`* would deny
the tagged column to every user including holders of `analyst`. The control
would not silently do nothing, as with groups — it would over-block, visibly and
for everybody, which is a different and louder failure than D7's.

Two adjacent facts checked while establishing this, because both could have
invalidated the deny shape independently:

- **Deny and exceptions *are* evaluated** even though egret's service-defs carry
  `"options": null` (`crates/egret-policy/src/service-defs/{trino,tag,starrocks}.json`).
  `ServiceDefUtil.getOption_enableDenyAndExceptionsInPolicies` (line 84-96)
  defaults the option to `true` via the hidden
  `ranger.servicedef.enableDenyAndExceptionsInPolicies` property, which egret
  does not set. Had this been false, `denyEvaluators` would be
  `Collections.emptyList()` (`RangerDefaultPolicyEvaluator.java:130-138`) and
  D1's whole deny shape would be inert. It is not.
- **`{public}` in a deny item still matches** with no group provider. The group
  check (`RangerDefaultPolicyItemEvaluator.java:127-129`) requires only
  `userGroups != null`, and `setUserGroups` normalises `null` to an empty set
  (line 294), so `policyItem.getGroups().contains(GROUP_PUBLIC)` is reached and
  is true. The "everyone" half of a deny/deny-exception pair is therefore
  expressible; only the "except these" half is not.

## 4. Consequences for the rest of SP4c

1. **Clearance compiles to an enumerated member list**, exactly as D7 forced for
   workspace members. A tag's `required_roles` is expanded at compile time into
   the bare usernames of the role's members, and those usernames go into
   `denyExceptions`. The Ranger `roles` bucket is not used.
2. **D3 gains its third trigger for real.** "Membership of a clearing role
   changing" is no longer conditional on D0 — it is required, and it must
   recompile in the same transaction as the membership write, through
   `services_and_tag_services_via`.
3. **A latent SP4a defect is now visible.** `crates/egret-perm-compile/src/grants.rs:105`
   compiles a `PrincipalKind::Role` grant straight into the Ranger `roles`
   bucket (`PrincipalKind::Role => roles.push(p.r#ref.clone())`). Per this
   measurement that grant matches nobody in the engine, while egret's own
   evaluator happily matches it (`crates/egret-perm/src/eval.rs:160`,
   `s.roles.iter().any(...)`) — so `explain` will report an access the engine
   does not grant. This is the same class of divergence D7 caught for groups,
   on a path D7 did not look at. It is out of D0's scope to fix; it should be
   raised as its own item rather than absorbed silently into SP4c.
4. **D2's group warning widens.** The UI cannot say "roles are enforced, groups
   are not", because the enforceable thing is neither: it is the *expanded
   member set at compile time*, which goes stale and is why trigger 3 exists.

## 5. What this measurement does not establish

- **StarRocks.** Everything above is measured on the Trino path. StarRocks has
  its own Ranger plugin and its own service-def
  (`crates/egret-policy/src/service-defs/starrocks.json`, also `options: null`),
  and its role handling was **not** examined. StarRocks does have native roles,
  so its plugin may populate `userRoles` where Trino's passes `null`. Do not
  carry this conclusion to StarRocks without measuring it.
- **The plugin's on-disk role cache.** `RangerRolesProvider` can load roles from
  `<cache.dir>/trino_<service>_roles.json` when the admin fetch fails. The
  cache directory on the running pod was not inspected, because that needs an
  `exec` into `demo-trino`, which is under a standing do-not-touch constraint.
  The mechanism makes the cache irrelevant — it can only ever replay a document
  a previous successful download wrote, and `lastKnownRoleVersion=-1` in the log
  shows no download ever succeeded — but the file itself was not listed.
- **A live clearance query.** `sp3c2-trino-live` no longer exists in
  `egret-engines` (only `demo-trino` runs), so the corroborating query D5 will
  need was not available and was not attempted. This result rests on upstream
  source plus a passive log read, which is the D7 standard.
