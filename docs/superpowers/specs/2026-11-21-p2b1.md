# P2-B1: StarRocks delegation user-sync cleanup (KI-358, KI-359)

Code: `crates/egret-engine-mgmt/src/starrocks_users.rs` (`sync_locked`).
Unit/fake-FE tests: `engines.rs` (`FakeStarRocksDdl`). The StarRocks round trip is
verified live separately.

## KI-359: a user created on StarRocks but never recorded

Root cause: `sync_locked` records a member in `engine_mgmt.starrocks_users`
BEFORE `CREATE USER`, then on ANY create failure forgets the record if this call
inserted it. When the FE ran the statement but the answer was lost (timeout,
dropped connection: an `FeError` with no FE error code), that deletes the only
evidence egret created the user; the next sync plans it `foreign` and, on a
no-profile engine, never grants the delegator `IMPERSONATE`.

Decision: forget only when the failure proves the statement did not run for this
call: the FE answered with an error code (a refusal) or said the user already
exists. A code-less failure is ambiguous and keeps the record. The next sync
then sees it recorded: on the FE means kept and granted; absent from the FE
means planned `create` again (a retry; an `already exists` then forgets it).
Idempotent.

Not done on purpose: adopting an unrecorded user that merely matches a member
name. Without a record egret cannot tell a lost create from a user an admin made
deliberately, and adopting would let egret DROP it later when the member leaves.
Users already stranded this way stay `foreign` (the KI-359 workaround still
applies to them).

## KI-358: grant on a user that no longer exists

`REVOKE IMPERSONATE ON USER <gone>` fails (`cannot find user`), so the delegator's
grant on a vanished user lingered, live again if the name is re-created.

Decision: on an engine that converges native grants (no profile), orphans =
(delegator's `ON USER` grants) minus `SHOW USERS` minus users created in this
sync. For each valid, non-reserved orphan name: `CREATE USER` with a random
password, `REVOKE IMPERSONATE ON USER ... FROM USER delegator`, `DROP USER`.
Chosen over `REVOKE ... ON ALL USERS` + re-grant of the live set because that
leaves a window where every member's queries fail, and a failed re-grant
would break members; the stand-in user is only ever a name nobody holds. If
the revoke fails the stand-in is still dropped (state returns to the previous
orphan, retried next sync). If `CREATE USER` fails (someone created the name
meanwhile) nothing else is sent. Bound (Ranger) engines read no native grant and
are untouched.
