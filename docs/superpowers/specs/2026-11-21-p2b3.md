# P2-B3: SQL Lab StarRocks explorer catalog (KI-338)

**Row.** The SQL Lab explorer of a StarRocks connection ran `SHOW DATABASES`
in the session's catalog, `default_catalog`, so it listed `_statistics_`,
`information_schema` and `sys` and never the external catalog the engine
serves (the one queries name as `<catalog>.<schema>.<table>`).

**Premise on main.** `SchemaService::catalogs` returned `[]` for StarRocks
("no catalog level"); the frontend showed `SchemaList` with `catalog=""`.
(The Trino explorer does not filter either; it lists `SHOW CATALOGS` as is.)

**Decisions.**
- StarRocks gets a catalog level. `catalogs` runs `SHOW CATALOGS` and drops the
  `Internal` one (`default_catalog`); what is left are the external catalogs
  egret provisions. The name is not configured anywhere on the connection, so
  the engine is the source of truth.
- `schemas`, `tables`, `columns` take the catalog and emit
  `SHOW DATABASES FROM`, `SHOW TABLES FROM c.s`, `DESCRIBE c.s.t`. An empty
  catalog keeps the old session-scoped statements (old clients).
- Statement builders and the catalog filter are pure functions, unit-tested.
- Frontend: `DataPanel` browses catalog -> schema -> table for StarRocks too.
- Not changed: object search on StarRocks (`information_schema.tables`, no
  catalog). Queries are untouched.
