## KI-236: the rule

**Browse stays as it is for `storage:read`. Downloading an object's bytes is refused (403, with the reason) to anyone who is not a platform admin when the object lies under the storage of a catalog:**

- the storage connection of every egret warehouse (`catalog.warehouses.storage_conn_id`: its bucket and Key prefix);
- the embedded lakekeeper's own storage profile of every warehouse (`lakekeeper.warehouse.storage_profile`: `bucket`, `key-prefix`), which is what the engines write to and does not move when the connection is edited later;
- the storage connection of every registered catalog bound to one (`registry.catalogs.storage_connection_id`: Iceberg on REST/Hive/Glue, Hive, Delta Lake, Hudi, whose tables live in that connection's storage).

A location without a prefix covers its whole bucket (a prefix-less warehouse claims the bucket in lakekeeper too). The match is on the key as the bucket sees it (connection Key prefix + key), ignores case and runs on every percent-decoding, the same way KI-206's rule does; buckets compare by name only, so an alias of the same server cannot reopen them (a same-named bucket elsewhere is over-closed, the safe side).

**Who may still download:** a platform admin only, the same exemption as KI-206 (the role already holds the platform's storage credentials and every bypass). No new permission. Considered and not taken: `storage:update` edits a registration, it does not imply reading data; `catalog_registry:create` can mint Catalog Clients, but treating it as an exemption would add a second rule beside KI-206's for no role that needs it.

**Why only downloads:** names and sizes are what `storage:read` is for (a data steward checks what a table holds on disk); the bytes are what masks and row filters protect.

**Download paths enumerated** (every route that returns object bytes to a `storage:read` holder):

| Path | Covered |
|---|---|
| `GET /api/control-plane/storage/{id}/download?key=` (Storage browser's Download link) | Yes, the only one |
| Presigned URLs | None exist (no presign anywhere in egret) |
| Preview of a storage object | None exists (`/storage/{id}/objects` returns names and sizes only) |
| Batch / zip download | None exists |

Other byte-serving routes are not gated by `storage:read` and do not read arbitrary keys: workflow execution file preview and namespace files (`workflow:read`, indexed files of the workspace only, under egret's own `workflow/` prefix, closed in Storage by KI-206), SQL Lab results (the owner's post-mask rows), Iceberg REST (Catalog Client grants, STS credentials scoped to the loaded table).

## KI-263: finish the swap in a task the request does not own

`apply_built` (engine-mgmt), the one chokepoint every provision/update goes through, now runs the provisioner call and the bookkeeping after it (catalog applied flags, internal secrets commit) in a `tokio::spawn`ed task and awaits it. A connected client gets the same result as before; a dropped request no longer cancels the task, so a Docker update that removed the old containers always starts the new ones, and the engine status (read live from the containers) goes `provisioning` → `running` on its own.

Why this and not the alternatives:

- It matches how egret-engine-mgmt already runs work that must not depend on the request: the StarRocks bootstrap (`spawn_starrocks_catalog_wire`) is a `tokio::spawn` over a cloned `CpState`. The Kubernetes provisioner does not need it as much (server-side apply, then Kubernetes rolls out on its own), but it gets the same protection for the bookkeeping after the apply.
- At the provisioner level (only Docker's `update`) the swap would finish, but the internal secrets the new containers were given would not be recorded when the request dropped (the monitor would fail until the next save).
- Reordering (start new, then remove old) is not possible on Docker: the containers have fixed names and pod-shaped hostnames.

Not changed: what the update handler does after `apply_built` (re-materializing workspace connections, restoring the stored spec on a failed apply) still runs in the request.
